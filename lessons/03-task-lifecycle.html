一次任务的生命周期Lifecycle of a Task

从你按下回车的那一刻，到 GenericAgent 说“任务完成”，中间发生了什么？这一课把一次任务的完整生命周期拆开看——它本质上就是一个会循环的对话：问大模型 → 大模型想调哪个工具 → 执行工具 → 把结果喂回去 → 再问，直到收尾。

🌍 宏观理解

整个生命周期就是一个 while 循环，最多跑 max_turns 轮（默认 40）。每一轮叫一个turn：把当前 messages 发给大模型，拿到回复；如果回复里有工具调用，就执行它们，把结果拼成下一轮的 messages；如果没有工具要调、或某个工具说“该退出了”，循环就结束。

一次任务，分步走

1

用户输入

你的请求作为 user_input 进入循环。

2

组装初始 messages

循环先拼出 [{system_prompt}, {user_input}] 作为对话起点。

3

调用大模型

client.chat(messages, tools=tools_schema) 返回一个 response，里面可能带 response.tool_calls。

4

解析工具调用

每个 tool_call 解析出 tool_name 和 args；如果模型没调任何工具，记为 no_tool。

5

派发并执行工具

handler.dispatch(tool_name, args, ...) 找到对应的 do_<tool> 方法并运行（如 do_code_run、do_file_read）。

6

返回 StepOutcome

每个工具返回 StepOutcome(data, next_prompt, should_exit)：data 是结果，next_prompt 是下一轮要对模型说的话，should_exit 决定是否收尾。

7

结果写回 messages

工具的 data 收进 tool_results，next_prompt 合成下一轮唯一的新 user 消息；历史由 Session 维护。

8

循环，直到收尾

没有 next_prompt、有工具 should_exit、或达到 max_turns，循环结束并返回 exit_reason。

循环的骨架

agent_loop.pyagent_runner_loop
while turn < handler.max_turns:
    turn += 1
    response = yield from client.chat(messages=messages, tools=tools_schema)

    # 没调工具就记为 no_tool
    tool_calls = [{'tool_name': tc.function.name, 'args': json.loads(tc.function.arguments)}
                  for tc in response.tool_calls]

    for tc in tool_calls:
        outcome = yield from handler.dispatch(tc['tool_name'], tc['args'], response)
        if outcome.should_exit: ...        # EXITED
        if not outcome.next_prompt: ...   # CURRENT_TASK_DONE
        tool_results.append(...)

    # 只把新消息带入下一轮，历史由 Session 保存
    messages = [{'role': 'user', 'content': next_prompt, 'tool_results': tool_results}]
🔬 源码对应

每一步都能在源码里指认到：

  • 循环本体：agent_loop.py: agent_runner_loop，初始 messages 就是 system_prompt + user_input。
  • 工具派发：agent_loop.py: BaseHandler.dispatch，用 do_<tool> 找到并执行对应方法（实现见 ga.py: GenericAgentHandler）。
  • 每步的结果契约：agent_loop.py: StepOutcome，三个字段 data / next_prompt / should_exit 决定循环何去何从。
  • 模型与工具调用：llmcore.py: chat 返回的 response 带 response.tool_calls，由循环逐个解析执行。

⚙️ messages 每轮如何重置

第一轮的 messages 是 [system, user]。之后每一轮的结尾，循环都会执行 messages = [{role: user, content: next_prompt, tool_results: tool_results}]——把 messages 整个换成一条新的 user 消息，而不是往里追加。完整对话历史不在 messages 里，而是由 LLM 客户端（Session/backend.history）保存。

❓ 为什么历史交给 Session 而不是 messages

源码那一行后面写着注释 # just new message, history is kept in *Session。把“增量”和“全量历史”分开，循环每轮只需搬运一小段新内容，逻辑极简；而历史的拼装、裁剪、省 token 都交给客户端统一处理。这正是上下文能长期压在 30K 以内的结构性原因。

2 三种退出条件，分别长什么样 点击展开
🧪 三种退出对照
exit_reason触发条件
EXITED某个工具返回 should_exit=True（如 ask_user 等待你回答）。
CURRENT_TASK_DONE某个工具的 next_prompt 为空——“没有下一句要说”，即任务完成。
MAX_TURNS_EXCEEDEDwhile 跑满 max_turns 仍未收尾，作为兜底返回。
⚙️ 内部怎么走

在工具循环里，源码先判 if outcome.should_exit: 置 EXITED 并 break；再判 if not outcome.next_prompt: 置 CURRENT_TASK_DONE 并 break。两者都没发生且 while 自然结束时，函数最后 return exit_reason or {'result': 'MAX_TURNS_EXCEEDED'}。

⚠️ 一个不显眼的“缓冲”：_done_hooks

“任务完成”不一定立刻结束：当没有 next_prompt 且没有 EXITED 时，循环会先看 handler._done_hooks 里有没有排队的收尾提示，有就再追加一轮。只有 EXITED 或 _done_hooks 也空了，才真正 break。读循环时别把“没有 next_prompt”直接等同于“马上停”。

@dataclass
class StepOutcome:
    data: Any
    next_prompt: Optional[str] = None
    should_exit: bool = False
⚙️ 三个字段各自的去向

data：工具的结果，若非空且非 no_tool，被序列化进 tool_results，随下一轮回传给模型。next_prompt：下一轮要对模型说的话；多个工具的 next_prompt 会汇入一个 set 再 '\n'.join(...)。should_exit：True 时直接置 EXITED 并 break。

❓ 为什么 next_prompt 同时管“说什么”和“是否结束”

一个字段兼任两职：有内容→继续，并把这段话作为下一轮的提问；为空（None/''）→视为“没有下一步”，即 CURRENT_TASK_DONE。这样循环不需要一个单独的“结束标志”——“无话可说”天然就是“做完了”，省掉一个状态，逻辑更紧凑。

⚙️ index 和 tool_num 是干嘛的

模型一轮可以请求多个工具调用。循环用 enumerate 遍历，把序号 index=ii 与总数 tool_num=len(tool_calls) 传进 dispatch。工具据此调整行为——例如 do_code_run 用 _tool_num 把单次输出上限均摊（10000 // _tool_num），多工具时每个少占点 token。

⚠️ 多工具时的提前退出

注意那两个 break：只要其中一个工具 should_exit 或交回空 next_prompt，整轮的工具循环就立刻中断，后面排队的工具不再执行。所以多工具调用不是“全部跑完再决定”，而是“边跑边可能提前收尾”。

🧩 生活类比

像一位主厨（大模型）和一名助手（循环）配合做菜。助手报一遍现状（messages），主厨说“去把洋葱切了”（tool_call）；助手照做（do_<tool>），把切好的洋葱和一句“切好了，下一步？”（StepOutcome 的 data + next_prompt）端回去；主厨再下一道指令。直到主厨说“齐活，上菜”（should_exit）——这一桌就完成了。

✅ 关键要点
  • 一次任务 = 一个 while 循环，每轮一个 turn，最多 max_turns（默认 40）。
  • 单轮节奏：chat → tool_calls → dispatch → do_<tool> → StepOutcome → 写回 messages。
  • StepOutcome 三字段是循环的“方向盘”：data、next_prompt、should_exit。
  • 结束有三种：should_exit、没有 next_prompt（任务完成）、达到 max_turns。
💡 设计亮点

注意那一行 messages = [{...新消息...}]：每轮只往下传一条新消息，而不是把越滚越长的历史整段重发。完整历史交给 Session 维护，循环只搬运“这一步的增量”。正是这个小设计，让上下文长期保持在 30K 以内——省 token、少噪声、更稳定，全都源于此。

From the moment you hit enter to the moment GenericAgent says "done", what actually happens? This lesson opens up the full lifecycle of one task. At heart it is a looping conversation: ask the LLM → the LLM picks a tool → run the tool → feed the result back → ask again, until it wraps up.

🌍 The Big Picture

The whole lifecycle is one while loop that runs at most max_turns times (default 40). Each pass is a turn: send the current messages to the LLM and get a reply; if the reply contains tool calls, run them and assemble their results into the next turn's messages; if there is no tool to call — or a tool says "time to exit" — the loop ends.

One task, step by step

1

User input

Your request enters the loop as user_input.

2

Assemble initial messages

The loop builds [{system_prompt}, {user_input}] as the conversation's starting point.

3

Call the LLM

client.chat(messages, tools=tools_schema) returns a response that may carry response.tool_calls.

4

Parse tool calls

Each tool_call yields a tool_name and args; if the model called nothing, it is recorded as no_tool.

5

Dispatch & run the tool

handler.dispatch(tool_name, args, ...) finds the matching do_<tool> method and runs it (e.g. do_code_run, do_file_read).

6

Return a StepOutcome

Each tool returns a StepOutcome(data, next_prompt, should_exit): data is the result, next_prompt is what to tell the model next turn, should_exit decides whether to wrap up.

7

Results flow into messages

Tool data collects into tool_results; the next_prompts merge into the single new user message; history is kept by the Session.

8

Loop until done

When there is no next_prompt, a tool signals should_exit, or max_turns is hit, the loop ends and returns an exit_reason.

The skeleton of the loop

Every step maps to a concrete spot in the source:

  • Tool dispatch: agent_loop.py: BaseHandler.dispatch looks up do_<tool> and runs it (implementations in ga.py: GenericAgentHandler).

How messages resets every turn

The first turn's messages is [system, user]. Then at the end of every turn, the loop runs messages = [{role: user, content: next_prompt, tool_results: tool_results}] — it replaces messages entirely with one new user message rather than appending to it. The full transcript does not live in messages; it is kept by the LLM client (the Session / backend.history).

Why hand history to the Session

The source line carries the comment # just new message, history is kept in *Session. Separating the "delta" from the "full history" lets the loop move only a small new chunk each turn, keeping its logic minimal; assembling, trimming and token-thrifting the history is all handled in one place by the client. That is the structural reason context stays under ~30K.

2 The three exit conditions, one by one click to expand
The three exits side by side
exit_reasonTrigger
EXITEDA tool returns should_exit=True (e.g. ask_user waits for your answer).
CURRENT_TASK_DONEA tool's next_prompt is empty — "nothing more to say", i.e. the task is done.
MAX_TURNS_EXCEEDEDThe while loop hits max_turns without wrapping up; returned as the fallback.
Under the hood

Inside the tool loop, the source first checks if outcome.should_exit: to set EXITED and break; then if not outcome.next_prompt: to set CURRENT_TASK_DONE and break. If neither fires and the while ends naturally, the function finally does return exit_reason or {'result': 'MAX_TURNS_EXCEEDED'}.

A subtle buffer: _done_hooks

A "done" task does not always stop immediately: when there is no next_prompt and no EXITED, the loop first checks whether handler._done_hooks has any queued wrap-up prompts, and if so it runs one more turn. Only EXITED, or an empty _done_hooks, truly breaks. When reading the loop, don't equate "no next_prompt" with "stop right now".

3 What StepOutcome's three fields actually carry click to expand
The dataclass source

@dataclass
class StepOutcome:
    data: Any
    next_prompt: Optional[str] = None
    should_exit: bool = False
Where each field flows

data: the tool's result; if non-empty and not no_tool, it is serialized into tool_results and sent back to the model next turn. next_prompt: what to say to the model next turn; multiple tools' next_prompts collect into a set, then '\n'.join(...). should_exit: when True, sets EXITED and breaks immediately.

Why next_prompt doubles as an end-signal

One field, two jobs: non-empty → continue, using that text as the next turn's prompt; empty (None/'') → treated as "no next step", i.e. CURRENT_TASK_DONE. So the loop needs no separate "finished" flag — "nothing left to say" naturally means "done", removing a state and keeping the logic compact.

What index and tool_num are for

The model can request several tool calls in one turn. The loop iterates with enumerate, passing the position index=ii and the total tool_num=len(tool_calls) into dispatch. Tools use these to adapt — e.g. do_code_run divides its output cap by _tool_num (10000 // _tool_num), so each tool takes fewer tokens when several run together.

Early exit among multiple tools

Note the two breaks: as soon as any one tool sets should_exit or returns an empty next_prompt, the whole turn's tool loop stops immediately and the remaining queued tools do not run. So a multi-tool turn is not "run them all, then decide" but "run them while possibly wrapping up early".

🧩 Analogy

Think of a head chef (the LLM) and an assistant (the loop) cooking together. The assistant recaps the situation (messages); the chef says "go dice the onions" (a tool_call); the assistant does it (do_<tool>) and brings back the diced onions plus "done, what next?" (a StepOutcome's data + next_prompt); the chef issues the next instruction. When the chef finally says "that's it, plate it up" (should_exit), the dish is complete.

✅ Key Takeaways
  • A task = one while loop; each pass is a turn, up to max_turns (default 40).
  • Per-turn rhythm: chat → tool_calls → dispatch → do_<tool> → StepOutcome → back into messages.
  • StepOutcome's three fields are the loop's steering wheel: data, next_prompt, should_exit.
  • Three ways to end: should_exit, no next_prompt (task done), or hitting max_turns.
💡 Design Insight

Notice the line messages = [{...new message...}]: each turn passes only one new message downward, instead of re-sending an ever-growing transcript. The full history is kept by the Session, and the loop carries just "the delta of this step". This small choice is exactly what keeps the context under ~30K — token-thrifty, low-noise and more stable, all from here.
