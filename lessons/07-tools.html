九个原子工具The Nine Atomic Tools

GenericAgent 只给大模型九个原子工具。就是这九件“最小够用”的工具，构成了它与外部世界交互的全部基础能力——代码、文件、网页、问人、记忆，五类齐活。

🌍 宏观理解

别的框架靠“工具多”取胜，GenericAgent 靠“工具少而通用”取胜。九个工具是正交的：每个负责一类最基本的动作，复杂能力不是再加新工具，而是用 code_run 写代码临时造出来。

九个原子工具

类别工具作用
代码 / 文件code_run执行任意代码（首选 Python，也可 PowerShell）。
file_read读文件（改前先读，拿到最新内容与行号）。
file_patch精确替换：把唯一匹配的旧内容换成新内容。
file_write创建 / 覆盖 / 追加文件（仅用于大段写入）。
网页web_scan感知网页：拿到简化 HTML 与标签页列表。
web_execute_js在真实浏览器里执行 JS 来操作网页。
问人ask_user遇到决策 / 缺信息 / 卡死时打断任务问用户。
记忆update_working_checkpoint短期工作便签，每轮自动注入，防长任务丢信息。
start_long_term_update启动长期记忆蒸馏，沉淀值得记住的经验。
🔬 源码对应
  • 九个工具的实现都是 do_<tool> 方法，集中在 ga.py: GenericAgentHandler（如 do_code_run、do_file_read、do_web_scan、do_ask_user、do_update_working_checkpoint…）。
  • 工具的“说明书”（名字、描述、参数）在 assets/tools_schema.json（中文版 assets/tools_schema_cn.json），由 agentmain.py 读入后交给循环。
  • 几个值得记的参数：code_run 用 script；file_patch 用 old_content / new_content（要求唯一精确匹配）；ask_user 可带 candidates 候选项。
🔬 源码：九个工具如何被“派发”

模型每轮输出工具名，agent_loop.py: BaseHandler.dispatch 据此拼出 do_<tool> 方法名并直接调用——“九个工具”其实就是九个 do_ 方法，没有插件系统、没有中间层。这就是“极简”与“强执行力”在源码层的交汇点。

agent_loop.pyBaseHandler.dispatch
def dispatch(self, tool_name, args, response, index=0, tool_num=1):
    method_name = f"do_{tool_name}"
    if hasattr(self, method_name):
        args['_index'] = index; args['_tool_num'] = tool_num
        ret = yield from try_call_generator(getattr(self, method_name), args, response)
        return ret
    # 未知工具 → 回一句提示给模型

🔬 深入源码

1 code_run：九个工具里的“元工具” 点击展开
🧪 script 参数 vs 回复代码块

tools_schema.json 写得很清楚：code_run “Prefer python. Multi-call OK, use script param. Reply code block is executed if no script arg”。也就是说——单次调用建议把代码直接放在回复的 ```代码块```（省去字符串转义），多次并发调用才用 script 参数。两者互斥。

⚙️ do_code_run 内部

ga.py: do_code_run 先取 args["code"] or args["script"]，没有就用 _extract_code_block(response) 从回复里抠代码块；默认 timeout=60、类型 python。输出有长度上限 maxlen = 10000 // _tool_num（按本轮工具数均分），所以 schema 才强调“No hardcoding bulk data”——大数据要落文件读，别塞进代码。

ga.pydo_code_run
def do_code_run(self, args, response):
    code = args.get("code") or args.get("script")
    if not code:                                  # 没传 → 从回复代码块里抠
        code = self._extract_code_block(response, code_type)
    timeout = int(args.get("timeout", 60))
    maxlen  = 10000 // args.get('_tool_num', 1)   # 输出预算按本轮工具数均分
    ...
❓ 为什么它是“元工具”

因为它能执行任意代码：运行时装包、调外部 API、写新脚本，甚至把一段临时能力固化成永久技能。正是这一个工具，把“只有九件工具”的极简框架变成能自我生长的系统——其余八个工具都是“感知 / 落盘 / 记忆”的边界，code_run 是“行动”的核心。

2 file_patch：唯一精确匹配，与它的坑 点击展开
🧪 唯一精确匹配规则

file_patch 的契约是“Replace unique old_content with new_content. Exact match required (whitespace/indentation)”。old_content 必须在文件里唯一且逐字符（含缩进/空白）匹配，否则拒绝替换——这逼模型先精确读、再精确改。

⚠️ 匹配失败怎么办

schema 直接给了药方：“On failure, file_read to recheck”。匹配不到通常是因为上下文不够独特、或空白/缩进对不上。正确做法是先 file_read 拿到最新内容与行号（schema：“Read before modify for latest context and line numbers”），再扩大 old_content 让它唯一。

🔀 file_patch vs file_write
file_patchfile_write
用途精细局部替换大段创建/覆盖/追加
schema 说唯一精确匹配HUGE edits ONLY
特性new_content 支持 {{file:..}} 引用支持 {{file:path:start:end}} 自动展开

默认改文件用 file_patch；只有整文件大改才动 file_write——这正是 part1 lesson_01 强调的“最小改动”原则在工具层的体现。

3 web_scan 与 web_execute_js：优先执行 JS，少扫 点击展开
⚙️ 两个工具的参数
工具关键参数
web_scantabs_only, switch_tab_id, text_only
web_execute_jsscript, save_to_file, no_monitor, switch_tab_id

web_scan 返回简化后的 HTML 与标签页列表（do_web_scan 默认 maxlen=35000//_tool_num），并会移除隐藏/浮动/被遮挡元素；web_execute_js 在真实浏览器里跑 JS，可用 save_to_file 把长结果落盘、no_monitor 跳过页面变化监控省 2–3 秒（仅限只读）。

❓ 为什么“优先 execute_js，少 scan”

tools_schema.json 在 web_execute_js 上写着“Act accurately to reduce web_scan calls”，在 web_scan 上注明 HTML 已被简化、边栏/浮动元素可能被滤掉。原因有二：scan 返回的简化 HTML 体积大、还可能漏内容；而 execute_js 能精确读取/操作 DOM，一步到位，既省 token 又更可靠。所以 scan 用来“感知一次”，execute_js 用来“反复操作”。

⚠️ do_web_execute_js 的取码与落盘

与 code_run 同构：do_web_execute_js 先取 args["script"]，没有就抠 ```javascript``` 块；若 script 是一个存在的文件路径，会读文件内容当脚本。给了 save_to_file 且有 js_return 时，完整结果写盘、回包里只留截断预览——避免长结果撑爆上下文。

4 update_working_checkpoint：每轮自动注入的工作便签 点击展开
⚙️ “每轮自动注入”是什么意思

do_update_working_checkpoint 把 key_info / related_sop 写进 self.working，并清零 passed_sessions。之后每一轮，_get_anchor_prompt() 会把这张便签连同近 30 条 [WORKING MEMORY] 历史一起拼进下一条 prompt——即使上下文被压缩，关键约束也不丢。

🧪 何时该调 / 不该调

schema 列出四个时机：(1) 读完 SOP 后存下用户需求与关键约束；(2) 切换子任务或上下文将被刷新前；(3) 反复失败后，重读 SOP 并存下新发现；(4) 新任务开始时更新内容、清空旧进度但保留有效约束。不要在简单 1–2 步任务、或任务已完成时调用——后者该用长期记忆工具。

⚠️ key_info 是“替换”不是“追加”

schema 强调 key_info “Replaces current notepad (<200 tokens)”，要做增量式更新：先回看现有内容，保留仍有效的，再增/删/改。便签很小（<200 token），所以只记坑点、用户硬性要求、关键参数/发现，不要写流水账。

5 start_long_term_update：跑完大任务后的“结算” 点击展开
⚙️ 它触发的是一段结算流程

do_start_long_term_update 不直接写记忆，而是开启结算：它注入一段“提炼经验”的提示词 + L0 记忆管理 SOP（memory/memory_management_sop.md），让 Agent 自己按 SOP 把验证成功且长期有效的环境事实 / 用户偏好 / 关键步骤，用 file_patch 最小化地写进 L2 / L3。

🧪 何时必须调用

schema 明确：“Must call when a task that took 15+ turns is completed”。其余时候是“发现值得记的环境事实 / 用户偏好 / 教训”时调用；若记忆已更新、或处于 autonomous 流程中，则跳过。

❓ 记什么、不记什么

注入的提示词划了红线：只记行动验证成功的信息——环境事实（路径/凭证/配置）、复杂任务的关键坑点/前置条件/重要步骤。禁止记临时变量、具体推理过程、未验证信息、通用常识、能轻松复现的细节。这正呼应 part1 的“自进化”：经验沉淀成 L3 的 *_sop.md，同类任务越做越快。

🧩 生活类比
像一把瑞士军刀：刀片不多，但每一片都通用。真碰到拧不动的特殊螺丝，你不会指望军刀上凭空多出一个专用旋具——而是用刀片这种“通用件”现做一个。GenericAgent 的 code_run 就是那把能“现做工具的刀片”。
✅ 关键要点
  • 九个工具五类：代码 / 文件（4）、网页（2）、问人（1）、记忆（2）。
  • 它们正交、最小够用；复杂能力靠 code_run 现场组合。
  • 实现看 ga.py 的 do_* 方法，描述看 assets/tools_schema.json。
💡 设计亮点
code_run 是九个工具里的“元工具”：因为它能执行任意代码，就能在运行时装包、调外部 API、写新脚本，甚至把一段临时能力固化成永久工具。正是这一个工具，把“只有九件工具”的极简框架，变成了一个能自我生长的系统——这也是后面“自进化机制”那一课的伏笔。

GenericAgent gives the model just nine atomic tools. These nine "minimal but sufficient" tools form the entire foundation for interacting with the outside world — code, files, web, asking the human, and memory: five categories in all.

🌍 The Big Picture

Other frameworks win by having many tools; GenericAgent wins by having few, general ones. The nine tools are orthogonal: each owns one basic kind of action, and complex capabilities are not added as new tools but improvised by writing code with code_run.

🔬 In the Source: how the nine tools are dispatched

Each turn the model emits a tool name; agent_loop.py: BaseHandler.dispatch builds the do_<tool> method name and calls it directly — the "nine tools" are literally nine do_ methods, with no plugin system and no middle layer. This is where "minimal" and "strong execution" meet in the source.

🔬 Deep Dive

1 code_run: the "meta-tool" among the nine click to expand
script param vs reply code block

tools_schema.json says it plainly: code_run "Prefer python. Multi-call OK, use script param. Reply code block is executed if no script arg". That is — for a single call, put code in a reply ```code block``` (no string escaping); use the script param only for multiple concurrent calls. The two are mutually exclusive.

Inside do_code_run

ga.py: do_code_run first reads args["code"] or args["script"], else extracts a code block from the reply via _extract_code_block(response); defaults to timeout=60, type python. Output is capped at maxlen = 10000 // _tool_num (split across this turn's tools), which is why the schema stresses "No hardcoding bulk data" — read bulk data from files, do not stuff it into code.

ga.pydo_code_run
def do_code_run(self, args, response):
    code = args.get("code") or args.get("script")
    if not code:                                  # none given → extract from the reply code block
        code = self._extract_code_block(response, code_type)
    timeout = int(args.get("timeout", 60))
    maxlen  = 10000 // args.get('_tool_num', 1)   # output budget split across this turn's tools
    ...
Why it is the "meta-tool"

Because it runs arbitrary code: install packages, call external APIs, write new scripts, even crystallize a temporary capability into a permanent skill at runtime. This single tool turns a "only nine tools" framework into a self-growing system — the other eight are the "perceive / persist / remember" boundary, and code_run is the core of "act".

2 file_patch: unique exact match, and its gotcha click to expand
The unique-exact-match rule

file_patch's contract is "Replace unique old_content with new_content. Exact match required (whitespace/indentation)". old_content must match uniquely and byte-for-byte (including indentation/whitespace), or the replace is rejected — forcing the model to read precisely before editing precisely.

What to do on a failed match

The schema prescribes the cure: "On failure, file_read to recheck". A miss usually means the context is not unique, or whitespace/indentation differs. The fix is to file_read for the latest content and line numbers (schema: "Read before modify for latest context and line numbers"), then widen old_content until it is unique.

Default to file_patch for edits; reach for file_write only for whole-file rewrites — the tool-level echo of the "minimal change" principle stressed in part1 lesson_01.

3 web_scan and web_execute_js: prefer execute_js, scan sparingly click to expand
Params of the two tools
ToolKey params
web_scantabs_only, switch_tab_id, text_only
web_execute_jsscript, save_to_file, no_monitor, switch_tab_id

web_scan returns simplified HTML plus the tab list (do_web_scan defaults to maxlen=35000//_tool_num) and strips hidden/floating/covered elements; web_execute_js runs JS in a real browser, can dump long results via save_to_file and skip change-monitoring with no_monitor to save 2–3s (reads only).

Why "prefer execute_js, scan sparingly"

tools_schema.json says on web_execute_js "Act accurately to reduce web_scan calls", and notes on web_scan that its HTML is simplified and sidebars/floating elements may be filtered out. Two reasons: scan's simplified HTML is large and may drop content, while execute_js reads/drives the DOM precisely in one shot — saving tokens and being more reliable. So scan is for "perceive once", execute_js for "act repeatedly".

Code source and save in do_web_execute_js

Isomorphic to code_run: do_web_execute_js reads args["script"], else extracts a ```javascript``` block; if script is an existing file path it loads that file as the script. When save_to_file is set and js_return exists, the full result is written to disk and only a truncated preview is returned — keeping long results from blowing up the context.

4 update_working_checkpoint: the auto-injected working notepad click to expand
What "auto-injected each turn" means

do_update_working_checkpoint writes key_info / related_sop into self.working and resets passed_sessions. Thereafter every turn, _get_anchor_prompt() stitches this notepad plus the recent [WORKING MEMORY] history into the next prompt — so key constraints survive even when context is compacted.

When to call / not call

The schema lists four moments: (1) after reading an SOP, store user needs and key constraints; (2) before switching subtasks or a context flush; (3) after repeated failures, re-read the SOP and store new findings; (4) on a new task, update content and clear old progress while keeping valid constraints. Do not call it for simple 1–2 step tasks, or once a task is complete — that is the long-term memory tool's job.

key_info replaces, not appends

The schema stresses key_info "Replaces current notepad (<200 tokens)" and should be updated incrementally: review what is there, keep what still holds, then add/remove/modify. The notepad is tiny (<200 tokens), so record only pitfalls, hard user requirements, and key params/findings — not a running log.

5 start_long_term_update: "settling up" after a big task click to expand
It triggers a settlement flow

do_start_long_term_update does not write memory directly; it opens a settlement: it injects a "distill lessons" prompt plus the L0 memory management SOP (memory/memory_management_sop.md), letting the agent follow that SOP to write verified, long-lived environment facts / user prefs / key steps into L2 / L3 with minimal file_patch edits.

When you must call it

The schema is explicit: "Must call when a task that took 15+ turns is completed". Otherwise call it when you discover environment facts / user prefs / lessons worth remembering; skip if memory is already updated or you are inside an autonomous flow.

What to record, what not to

The injected prompt draws a red line: record only action-verified info — environment facts (paths/credentials/config) and a complex task's key pitfalls/preconditions/steps. Forbidden: temporary variables, detailed reasoning, unverified info, general knowledge, easily reproducible details. This echoes part1's "self-evolution": experience crystallizes into L3 *_sop.md, so similar tasks get faster over time.

🧩 Analogy
Like a Swiss Army knife: few blades, but each is general. When you hit an oddly shaped screw, you do not expect a dedicated driver to appear out of nowhere — you improvise one using the general blades. GenericAgent's code_run is exactly that "blade that makes other tools on the spot".
✅ Key Takeaways
  • Nine tools in five groups: code/file (4), web (2), human (1), memory (2).
  • They are orthogonal and minimal; complex capability is composed on the fly via code_run.
  • See ga.py do_* methods for implementations and assets/tools_schema.json for descriptions.
