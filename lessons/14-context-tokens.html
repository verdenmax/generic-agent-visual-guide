上下文工程与 Token 效率Context Engineering & Token Efficiency

别的 Agent 动辄吞下 200K–1M 的上下文，GenericAgent 却把自己控制在 <30K 以内。上下文小，不只是省钱——更意味着噪声更少、幻觉更少、成功率更高。这一课看 GA 是怎么做到的。

🌍 宏观理解

GA 的省 token 不是某一个开关，而是一整套“只留当下需要的”的习惯：历史不堆进 messages、展示给模型的内容会被压缩、长长的工具参数会被精简、工具描述每隔几轮重置一次。再加上分层记忆与工作便签托底，“忘掉原始历史”反而不丢关键信息。

  • 历史侧压缩在 llmcore.py: compress_history_tags / trim_messages_history（保留最近若干轮，压缩/截断更早的内容）。

1 _clean_content：把展示内容“缩骨” 点击展开
🧪 真实实现
agent_loop.py_clean_content
def _clean_content(text):
    def _shrink_code(m):
        body = [l for l in lines[1:-1] if l.strip()]
        if len(body) <= 6: return m.group(0)
        preview = '\n'.join(body[:5])
        return f'```{lang}\n{preview}\n  ... ({len(body)} lines)\n```'
    text = re.sub(r'```[\s\S]*?```', _shrink_code, text)
    for p in [r'<file_content>[\s\S]*?</file_content>',
              r'<tool_(?:use|call)>[\s\S]*?</tool_(?:use|call)>', r'(\r?\n){3,}']:
        text = re.sub(p, ..., text)
    return text.strip()
⚙️ 三步缩骨

① 任何代码块若非空行超过 6 行，只留前 5 行再加一句 ... (N lines)；② 删掉 <file_content> 与 <tool_use|tool_call> 整块；③ 三个以上连续换行压成两个。注意它只用于 verbose=False 的展示路径，目的是让终端输出干净、不刷屏。

2 _compact_tool_args：参数也要瘦身 点击展开
🧪 真实实现
agent_loop.py_compact_tool_args
def _compact_tool_args(name, args):
    a = {k: v for k, v in args.items() if k != '_index'}
    for k in ('path',):
        if k in a: a[k] = os.path.basename(a[k])
    if name == 'update_working_checkpoint':
        s = a.get('key_info', ''); return (s[:60]+'...') if len(s)>60 else s
    s = json.dumps(a, ensure_ascii=False)
    return (s[:120]+'...') if len(s)>120 else s
⚙️ 为什么要精简参数显示

工具参数里常有长绝对路径、整段脚本。展示时 _compact_tool_args 把 path 只留 basename、整体 JSON 超 120 字就截断，并对 update_working_checkpoint、ask_user 等做专门精简。它服务于 verbose=False 下 🛠️ name(args) 这一行——既能一眼看清在调什么，又不把屏幕撑爆。

⚠️ 坑点：只是显示层，不改实际参数

_clean_content 与 _compact_tool_args 都只影响给人看的输出，不会改写真正发给工具的 args，也不改发给模型的历史。真正省 token 的“历史压缩”在 llmcore 那一侧（下一个折叠）。别把这两者误当成上下文压缩——它们是“终端整洁术”。

def compress_history_tags(messages, keep_recent=10, max_len=800, force=False, interval=5):
    if compress_history_tags._cd % interval != 0: return messages
    for i, msg in enumerate(messages):
        if i >= len(messages) - keep_recent: break  # 最近若干轮不动
        # 把 <thinking>/<tool_use>/<tool_result> 等标签内容截断
🧪 超额就丢最老的
llmcore.pytrim_messages_history
def trim_messages_history(history, sess):
    cap = sess.context_win * 3
    compress_history_tags(history, interval=...)
    if cost() <= cap: return
    compress_history_tags(history, keep_recent=4, force=True)
    while len(history) > 9 and cost() > target:
        history.pop(0)  # 从最老的开始丢
⚙️ 两段式策略

每次 *Session.ask 发请求前都会调 trim_messages_history：先轻压——周期性把较老消息里的 thinking/tool 标签内容截短（保留最近 ~10 轮）；若仍超过 context_win*3 字符的硬上限，再强压（keep_recent=4）并从最老消息开始 pop，直到降到目标线。这才是把上下文常年压在 <30K 的真正机制。

💡 设计亮点
小上下文不是妥协，而是 GenericAgent 主动选择的特性。它敢于“忘掉”原始历史，靠的是前几课的两块基石：分层记忆把该长期留的沉淀到 L1–L4，工作便签把当下该记的每轮回灌。于是上下文越小、信号越纯、越不容易跑偏——长任务反而更稳。这正是 GA “少即是多”哲学在运行时最直接的体现。

Other agents swallow 200K–1M tokens of context; GenericAgent keeps itself under <30K. A small context is not just cheaper — it means less noise, fewer hallucinations, and a higher success rate. This lesson shows how GA pulls it off.

🌍 The Big Picture

GA's token thrift is not a single switch but a whole set of "keep only what is needed now" habits: history is not piled into messages, content shown to the model is compacted, long tool arguments are trimmed, and tool descriptions reset every few turns. Backed by layered memory and the working notepad, "forgetting raw history" loses nothing essential.

Three shrinking steps

① any code block whose non-empty lines exceed 6 keeps only the first 5 plus a ... (N lines) line; ② strip whole <file_content> and <tool_use|tool_call> blocks; ③ collapse 3+ consecutive newlines into two. Note it only runs on the verbose=False display path, to keep terminal output clean and unflooded.

Why compact the arg display

Tool args often hold long absolute paths or whole scripts. For display, _compact_tool_args keeps only the basename of path, truncates the overall JSON past 120 chars, and special-cases tools like update_working_checkpoint and ask_user. It serves the 🛠️ name(args) line under verbose=False — readable at a glance without blowing up the screen.

Pitfall: display-only, not the real args

Both _clean_content and _compact_tool_args affect only the human-facing output; they never rewrite the real args passed to a tool, nor the history sent to the model. The real token-saving "history compression" lives on the llmcore side (next accordion). Do not mistake these two for context compression — they are the "tidy-terminal" art.

A two-stage strategy

Before every *Session.ask request, trim_messages_history runs: first a light pass — periodically truncating thinking/tool-tag content in older messages (keeping the latest ~10 turns); if still over the hard cap of context_win*3 chars, a hard pass (keep_recent=4) plus popping from the oldest message until it drops below the target. This is the real mechanism keeping context under ~30K.

🧩 Analogy
Like a tidy workbench: only the parts for the current step sit at hand, and finished ones are filed into drawers; the surface stays clean, so you find things fast and rarely grab the wrong one. GA's context management is exactly this "tidy-desk" art — not remembering less, but putting only what belongs on the desk, on the desk.
✅ Key Takeaways
  • Goal: keep context under 30K — less noise, fewer hallucinations, lower cost.
  • A combo: only-new-message + _clean_content + _compact_tool_args + periodic reset + history compression.
  • Layered memory + the working notepad backstop it, so "forgetting raw history" loses nothing essential.
💡 Design Insight
A small context is not a compromise but a feature GenericAgent chooses. It dares to "forget" raw history thanks to two foundations from earlier lessons: layered memory settles what should persist into L1–L4, and the working notepad re-injects what matters now each turn. So the smaller the context, the purer the signal and the less it drifts — long tasks become more stable, not less. This is GA's "less is more" philosophy at its most direct, at runtime.
