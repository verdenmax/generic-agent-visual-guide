LLM 内核 llmcore.pyThe LLM Core

循环只调用一个方法——client.chat(messages, tools)。至于背后是 Claude、GPT，还是 Kimi、DeepSeek；是“原生函数调用”还是“纯文本协议”——这些差异全被 llmcore.py 抹平，对外只露出一个统一的、可流式的 chat 接口。

🌍 宏观理解

llmcore 干两件事：① 适配——把各家不同的请求/响应格式翻译成 GA 内部统一的对象；② 流式——一边把模型吐出的字实时显示给你，一边在结束时把回复解析成结构化的 tool_calls。它原生支持 OpenAI 兼容接口与 Anthropic Claude 原生接口两套协议。

两种工具协议

原生函数调用

把工具 schema 交给支持 function-calling 的模型 API，直接拿回结构化的 tool_calls。实现见 NativeToolClient。

纯文本协议

对不支持函数调用的模型，先把工具说明拼进提示词，再从模型的文本回复里把工具调用解析出来。实现见 ToolClient。

🔬 源码对应
  • 两个客户端：ToolClient（文本协议）与 NativeToolClient（原生协议），都提供 chat(messages, tools)。
  • 多种会话后端：ClaudeSession / LLMSession / NativeClaudeSession / NativeOAISession，并由 MixinSession 聚合多个后端；通过 api_mode 在 chat_completions 与 responses 之间切换。
  • 流式由 SSE 解析器处理（_parse_openai_sse / _parse_claude_sse）；不同协议的工具调用统一成 MockResponse / MockToolCall，所以循环永远只看到同一种 response 对象。

1 文本协议 vs 原生协议：两个 chat 的根本差异 点击展开
🧪 ToolClient.chat（文本协议）
llmcore.pyToolClient.chat
def chat(self, messages, tools=None):
    full_prompt = self._build_protocol_prompt(messages, tools)
    gen = self.backend.ask(full_prompt)
    raw_text = ''
    for chunk in gen:
        raw_text += chunk; yield chunk
    return self._parse_mixed_response(raw_text)
🧪 NativeToolClient.chat（原生协议）
llmcore.pyNativeToolClient.chat
def chat(self, messages, tools=None):
    if tools: self.backend.tools = tools
    # 把 messages 拼成一条 user，含 tool_result 块
    merged = {'role': 'user', 'content': final_content}
    gen = self.backend.ask(merged)
    try:
        while True: chunk = next(gen); yield chunk
    except StopIteration as e: resp = e.value
    return resp
🔀 区别在哪

ToolClient：模型不支持原生 function-calling，于是把工具协议写进纯文本提示词（_build_protocol_prompt 注入“交互协议 + Tools JSON”），再用正则从混合文本里解析出 <tool_use> 块。NativeToolClient：模型支持原生工具调用，直接传 content-block，工具调用由 API 原生返回，无需文本解析。两者都返回同一种 MockResponse，所以上层循环看不出区别。

❓ 为什么要 Mixin

单个 API 会限流或抖动。MixinSession 把若干同组（全 Native 或全非 Native）后端串成一条容错链：主后端失败就轮换到下一个，过了 spring_back 秒再弹回主后端。它用 __getattr__/__setattr__ 把属性广播到所有子会话，对上层伪装成“一个会话”。

⚙️ 归一化为什么重要

Claude 返回 content-block，OpenAI 返回 delta+tool_calls，responses API 又是另一套事件名。各解析器先把它们统一成 list[content_block]，再包成 MockResponse(thinking, content, tool_calls, raw)。于是 agent_loop.py 里 response.tool_calls、tc.function.name/arguments 这套字段对任意模型都成立——多协议的复杂性被锁死在 llmcore 内。

4 api_mode：chat_completions 与 responses 的切换点 点击展开
🧪 解析为枚举
llmcore.pyBaseSession.__init__
mode = str(cfg.get('api_mode', 'chat_completions')).strip().lower().replace('-', '_')
self.api_mode = 'responses' if mode in ('responses', 'response') else 'chat_completions'
⚙️ 两种模式怎么影响下游

api_mode 一路传到 _parse_openai_sse 与 _record_usage：

  • chat_completions：读 choices[0].delta.content / tool_calls，用量字段是 prompt_tokens / completion_tokens。
  • responses：读 response.output_text.delta 与 response.function_call_arguments.delta，用量是 input_tokens / output_tokens（含 cached）。
⚠️ 坑点：配置名会被归一化

写 api_mode: "response"（少个 s）或 "chat-completions"（连字符）都不会报错——初始化时会 strip().lower().replace('-','_') 并把 response/responses 都收敛到 'responses'，其余一律当 'chat_completions'。容错，但也意味着拼错的非法值会静默落到默认值。

🧩 生活类比
像一个万能电源适配器：欧标、美标、英标插头形状各异，适配器统一转成你设备要的那一种。llmcore 就是模型世界的适配器——无论模型“插头”长什么样，循环拿到的永远是同一个标准接口。
✅ 关键要点
  • 对外只有一个统一入口 chat(messages, tools)，屏蔽所有模型差异。
  • 两种工具协议：原生函数调用（NativeToolClient）与纯文本协议（ToolClient）。
  • 不同协议的回复统一成 MockResponse / MockToolCall，循环无需关心来源。
💡 设计亮点
chat() 是个生成器：它一边 yield 流式字符，一边在结束时 return 解析好的结构化回复。这正是循环里那句 response = yield from client.chat(...) 能同时拿到“实时输出”和“最终结果”的原因。更妙的是文本协议这条退路——它让连函数调用都不支持的模型也能用上工具，把 GA 的“高兼容性”落到了实处。

The loop calls just one method — client.chat(messages, tools). Whether the backend is Claude, GPT, Kimi or DeepSeek; whether it does "native function calling" or a "plain-text protocol" — all those differences are flattened by llmcore.py, which exposes one unified, streamable chat interface.

🌍 The Big Picture

llmcore does two things: (1) adaptation — translating each vendor's request/response shapes into GA's unified internal objects; and (2) streaming — showing the model's tokens live while parsing the finished reply into structured tool_calls. It natively supports both the OpenAI-compatible and the Anthropic Claude native protocols.

Two tool protocols

Native function calling

Hand the tools schema to a model API that supports function calling and get structured tool_calls back directly. See NativeToolClient.

Plain-text protocol

For models without function calling, weave the tool instructions into the prompt, then parse tool calls out of the model's text reply. See ToolClient.

🔬 In the Source
  • Two clients: ToolClient (text protocol) and NativeToolClient (native protocol), both exposing chat(messages, tools).
  • Several session backends: ClaudeSession / LLMSession / NativeClaudeSession / NativeOAISession, aggregated by MixinSession; the api_mode switches between chat_completions and responses.
  • Streaming is handled by SSE parsers (_parse_openai_sse / _parse_claude_sse); tool calls from any protocol are normalized into MockResponse / MockToolCall, so the loop always sees the same kind of response object.

Where they differ

ToolClient: the model has no native function-calling, so the tool protocol is written into a plain-text prompt (_build_protocol_prompt injects the "interaction protocol + Tools JSON"), and <tool_use> blocks are regex-parsed back out of the mixed text. NativeToolClient: the model supports native tool calls, so it passes content-blocks directly and tool calls come back natively, with no text parsing. Both return the same MockResponse, so the loop above cannot tell them apart.

Why Mixin

A single API can rate-limit or flake. MixinSession chains several same-group (all-Native or all-non-Native) backends into a fault-tolerant chain: if the primary fails it rotates to the next, then springs back to the primary after spring_back seconds. It broadcasts attributes to all sub-sessions via __getattr__/__setattr__, disguising itself as "one session" to the caller.

Why normalization matters

Claude returns content-blocks, OpenAI returns deltas + tool_calls, and the responses API uses yet another set of event names. Each parser first unifies them into list[content_block], then wraps them as MockResponse(thinking, content, tool_calls, raw). So in agent_loop.py the fields response.tool_calls and tc.function.name/arguments hold for any model — the multi-protocol complexity is sealed inside llmcore.

4 api_mode: the switch between chat_completions and responses click to expand
Parsed into an enum
llmcore.pyBaseSession.__init__
mode = str(cfg.get('api_mode', 'chat_completions')).strip().lower().replace('-', '_')

How the two modes affect the rest

api_mode flows all the way to _parse_openai_sse and _record_usage:

  • chat_completions: reads choices[0].delta.content / tool_calls; usage fields are prompt_tokens / completion_tokens.
  • responses: reads response.output_text.delta and response.function_call_arguments.delta; usage is input_tokens / output_tokens (with cached).
Pitfall: the config value is normalized

Writing api_mode: "response" (missing the s) or "chat-completions" (hyphen) raises no error — init runs strip().lower().replace('-','_') and folds both response/responses to 'responses', treating anything else as 'chat_completions'. Forgiving — but it also means a mistyped invalid value silently falls back to the default.

🧩 Analogy
Like a universal power adapter: EU, US, UK plugs all look different, and the adapter converts them to the one your device needs. llmcore is that adapter for the model world — whatever a model's "plug" looks like, the loop always receives the same standard interface.
✅ Key Takeaways
  • There is one unified entry, chat(messages, tools), hiding all model differences.
  • Two tool protocols: native function calling (NativeToolClient) and text protocol (ToolClient).
  • Replies from any protocol become MockResponse / MockToolCall, so the loop need not care about the source.
💡 Design Insight
chat() is a generator: it yields streaming characters while returning the parsed, structured reply at the end. That is exactly why the loop's response = yield from client.chat(...) gets both "live output" and the "final result". Even better is the text-protocol fallback — it lets models without function calling still use tools, making GA's "high compatibility" real.
