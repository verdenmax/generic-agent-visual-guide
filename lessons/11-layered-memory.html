分层记忆系统 L0–L4Layered Memory (L0–L4)

GenericAgent 的记忆不是一锅粥，而是一座金字塔：从最顶上的“铁律”，到一份极简索引、一个事实库、一摞可复用的 SOP，再到最底层归档的历史会话。层层向下越来越细，向上越来越短。

🌍 宏观理解

为什么要分层？因为上下文很贵。GA 让上层只放“能指向下层的最短指针”：平时只加载极简的索引，真需要细节时再顺着指针去读对应的事实或 SOP。这样既不丢信息，又把每次喂给模型的上下文压到最小。

五层记忆

L0元规则 / Meta Rules
最高优先级的行为铁律——如“无行动，不记忆”“禁止存易变状态”。见 memory/memory_management_sop.md 的核心公理。
L1索引 / Insight Index
极简导航索引（global_mem_insight.txt，硬约束 ≤ 30 行），只留能定位 L2/L3 的最短标识。
L2事实库 / Global Facts
经行动验证的稳定知识（global_mem.txt）：路径、凭证、配置等长期有效的事实。
L3技能 / Task Skills · SOPs
可复用的工作流：memory/ 下的一摞 .md / .py（如 plan_sop.md、verify_sop.md）。这是“技能”真正住的地方。
L4归档 / Session Archive
历史会话存档（memory/L4_raw_sessions/），由 reflect/scheduler 自动收集，供长程回溯定位过往上下文。
🔬 源码对应
  • 层级架构与各层职责写在 memory/memory_management_sop.md（含 L1→L2→L3→L4 的“指针 → 引用”导航链）。
  • L3 就是 memory/ 目录本身：里面是一堆 *_sop.md（plan_sop、verify_sop、github_contribution_sop…）。
  • L4 在 memory/L4_raw_sessions/，由 reflect/scheduler.py 的反射任务自动归集。

1 L0 核心公理：四条最高优先级的铁律 点击展开
🧪 SOP 原文
memory/memory_management_sop.md0. 核心公理
1. 行动验证原则 — 只有“成功的工具调用结果”才能写入 L1/L2/L3。
   # No Execution, No Memory
2. 神圣不可删改性 — 已验证的配置/避坑指南重构时严禁丢弃，只能压缩或迁移层级。
3. 禁止存储易变状态 — 时间戳、Session ID、PID、临时绝对路径一律不存。
4. 最小充分指针 — 上层只留能定位下层的最短标识，多一词即冗余。
❓ 为什么 L0 是“公理”而不是代码

L0 不是某个函数，而是一份给模型读的宪法。每次结算长期记忆时，do_start_long_term_update 都会把这份 SOP 全文 （file_read('./memory/memory_management_sop.md')）作为工具结果回灌，让模型在动手改记忆前先复诵铁律。约束写在数据里、由模型遵守，而不是写死在代码里——这正是“极简种子”的风格。

每轮系统提示里只挂 L1 的 global_mem_insight.txt（≤30 行）。模型看到某个场景关键词 → 顺“指针”决定去读 L2 的某个 ## [SECTION] 拿事实，或顺“引用”去 ls memory/ 找对应的 *_sop.md 读详细步骤，更老的上下文才去 L4 翻历史会话。常驻上下文只有索引，细节按需逐层下钻。

3 “最小充分指针”：为什么 L1 硬卡在 ≤30 行 点击展开
🧪 同步红线（反例 → 正例）
memory/memory_management_sop.mdL1 ↔ L2/L3 同步规则
# L1 只写关键词/名称，禁搬细节
❌ sop_name(场景A:方法1+方法2+方法3)
✅ sop_name(场景A)
# 名字已自解释时连触发词都省略
❌ discord_slate_sop(Slate输入框)
✅ discord_slate_sop
❓ 为什么不把细节都写进索引

索引是每轮都要进上下文的；它越胖，每轮越贵、噪声越多。“最小充分指针”要求 L1 只回答“有没有这个能力 + 去哪找”，绝不回答“怎么做”。怎么做属于 L3，用到时才 file_read。把索引压到 ≤30 行，是 GA 在 <30K 上下文里仍“知道很多”的关键技巧。

🔀 对比：把一切塞进一个大记忆文件

若把事实、步骤、历史全堆在一个文件里，每轮都要带着这坨东西，上下文迅速爆炸且充满无关信息。分层 + 指针让“记得多”与“每轮只加载一点”不再矛盾——这正是 L0 第 4 条公理的工程兑现。

🧩 生活类比
像一本整理得很好的活页笔记：封面写着几条铁律（L0），第一页是目录（L1），后面是事实速查页（L2），再后面是一篇篇“怎么做某事”的食谱（L3），最后附着一摞旧日记（L4）。你平时只翻目录，需要时才按页码翻到具体那一篇。
✅ 关键要点
  • 五层：L0 铁律 · L1 索引 · L2 事实 · L3 技能/SOP · L4 会话归档。
  • 上层只放“最短指针”，按需顺着指针读下层细节。
  • L3（memory/ 下的 SOP）就是技能真正存放的地方。
💡 设计亮点
分层的精髓是“最小充分指针”：每往上一层，只保留刚好够定位下一层的那点信息，多一个词都算冗余。正因为索引被压到 ≤ 30 行，GA 才能把“我知道很多东西”和“每次只加载一点点”这对矛盾同时满足——这也是它能在 <30K 上下文里稳定工作的记忆侧根基。

GenericAgent's memory is not one big soup but a pyramid: from the "iron rules" at the top, down to a tiny index, a facts store, a stack of reusable SOPs, and finally archived past sessions at the bottom. Each layer down is more detailed; each layer up is shorter.

🌍 The Big Picture

Why layer it? Because context is expensive. GA keeps upper layers holding only "the shortest pointer to the layer below": normally it loads just the tiny index, and only follows a pointer to a fact or SOP when detail is actually needed. No information is lost, yet the context fed to the model each time stays minimal.

Five memory layers

L0Meta Rules
Top-priority behavioral rules — e.g. "No execution, no memory", "Do not store volatile state". See the core axioms in memory/memory_management_sop.md.
L1Insight Index
A tiny navigation index (global_mem_insight.txt, hard cap ≤ 30 lines) holding only the shortest locators into L2/L3.
L2Global Facts
Action-verified, stable knowledge (global_mem.txt): paths, credentials, configs and other long-lived facts.
L3Task Skills · SOPs
Reusable workflows: a stack of .md / .py under memory/ (e.g. plan_sop.md, verify_sop.md). This is where "skills" actually live.
L4Session Archive
Archived past sessions (memory/L4_raw_sessions/), auto-collected by reflect/scheduler, for long-horizon recall of earlier context.
🔬 In the Source
  • The layer architecture and each layer's duties are written in memory/memory_management_sop.md (including the "pointer → reference" navigation chain L1→L2→L3→L4).
  • L3 is the memory/ directory itself: a pile of *_sop.md files (plan_sop, verify_sop, github_contribution_sop …).
  • L4 lives in memory/L4_raw_sessions/, auto-collected by reflection tasks in reflect/scheduler.py.

🔬 Deep Dive

1 L0 core axioms: the four highest-priority iron rules click to expand
Straight from the SOP
memory/memory_management_sop.md0. Core Axioms
1. Action-Verified Only — only "successful tool-call results" may be written to L1/L2/L3.
   # No Execution, No Memory
2. Sanctity of Verified Data — verified config/pitfall notes may never be dropped on refactor — only compress or migrate.
3. No Volatile State — no timestamps, session IDs, PIDs, or transient absolute paths.
4. Minimum Sufficient Pointer — upper layers keep only the shortest locator for the layer below; one extra word is redundant.
Why L0 is "axioms", not code

L0 is not a function but a constitution the model reads. Every long-term settlement, do_start_long_term_update feeds the full SOP text back as a tool result (file_read('./memory/memory_management_sop.md')) so the model recites the iron rules before touching memory. The constraints live in data and are honored by the model, not hard-coded — exactly the "minimal seed" style.

How one navigation flows

Each turn the system prompt only carries L1's global_mem_insight.txt (≤30 lines). The model sees a scenario keyword → follows the "pointer" to read a ## [SECTION] of L2 for facts, or follows the "reference" to ls memory/ and read the matching *_sop.md for detailed steps; only older context reaches into L4 session history. Only the index stays resident; detail is drilled into layer by layer on demand.

Why not put detail into the index

The index goes into context every single turn; the fatter it is, the costlier and noisier each turn. The "minimum sufficient pointer" requires L1 to answer only "does this capability exist + where to find it", never "how to do it". The how-to belongs to L3 and is file_read only when needed. Squeezing the index to ≤30 lines is the key trick that lets GA still "know a lot" within a <30K context.

vs cramming everything into one big memory file

If facts, steps and history were all piled into one file, every turn would carry that lump, blowing up context with irrelevant information. Layering + pointers makes "remember a lot" and "load only a little each turn" no longer contradictory — the engineering payoff of L0's 4th axiom.

🧩 Analogy
Like a well-organized loose-leaf notebook: the cover lists a few iron rules (L0), the first page is the table of contents (L1), then a facts cheat-sheet (L2), then "how to do X" recipes (L3), and finally a stack of old diaries (L4). You usually only read the contents page and flip to a specific recipe by its number when needed.
✅ Key Takeaways
  • Five layers: L0 rules · L1 index · L2 facts · L3 skills/SOPs · L4 session archive.
  • Upper layers hold only "the shortest pointer"; follow it to read lower-layer detail on demand.
  • L3 (the SOPs under memory/) is where skills actually live.
💡 Design Insight
The essence of layering is the "minimum sufficient pointer": each layer up keeps just enough to locate the layer below — one extra word is redundancy. Because the index is squeezed to ≤ 30 lines, GA can satisfy both "I know a lot" and "I load only a little each time" at once — the memory-side foundation for working steadily within a <30K context.
