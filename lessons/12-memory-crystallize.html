记忆的读写与结晶Memory & Crystallization

分好层只是“书架”，还得有人往上面记东西。GenericAgent 用两个记忆工具完成读写：一个是任务进行中的“工作便签”，一个是任务收尾时的“长期记忆结算”。前者防遗忘，后者把经验结晶成技能。

🌍 宏观理解

短期：update_working_checkpoint 把“用户要什么、关键约束”写进一个便签，之后每轮自动注入，防止长任务跑着跑着把目标跑丢。长期：start_long_term_update 在任务完成后启动“结算”，把经过行动验证的环境事实/用户偏好/踩坑经验，最小化地写进 L1/L2/L3。

🔬 源码对应
  • 短期便签：ga.py: do_update_working_checkpoint 把 key_info / related_sop 写进 self.working，再由“锚点提示”每轮回灌给模型。
  • 长期结算：ga.py: do_start_long_term_update 注入一段提炼提示词，引导用 file_patch 最小化更新 L2 事实、同步 L1 索引、必要时精简 L3 SOP。
  • 结算受 L0 铁律约束：memory/memory_management_sop.md——只记“行动验证成功”的信息，禁存易变状态，能不改就不 overwrite、宁愿少量 patch。

1 短期便签：do_update_working_checkpoint 与每轮回灌的锚点 点击展开
🧪 工具本体
ga.pyGenericAgentHandler.do_update_working_checkpoint
def do_update_working_checkpoint(self, args, response):
    key_info = args.get('key_info', '')
    related_sop = args.get('related_sop', '')
    if 'key_info' in args: self.working['key_info'] = key_info
    if 'related_sop' in args: self.working['related_sop'] = related_sop
    yield '[Info] Updated key_info and related_sop.\n'
    next_prompt = self._get_anchor_prompt(skip=args.get('_index', 0) > 0)
    return StepOutcome({'result': 'working key_info updated'}, next_prompt=next_prompt)
🧪 锚点提示如何回灌
ga.pyGenericAgentHandler._get_anchor_prompt
def _get_anchor_prompt(self, skip=False):
    if skip: return '\n'
    prompt = f'\n### [WORKING MEMORY]\n{earlier}<history>\n{h_str}\n</history>'
    if self.working.get('key_info'):
        prompt += f'\n<key_info>{self.working.get(...)}</key_info>'
    return prompt
⚙️ 为什么叫“便签”

checkpoint 把 key_info / related_sop 写进 self.working（一个普通 dict，进程级、不落盘）。此后每个工具收尾都调 _get_anchor_prompt()，把 working memory 连同最近历史拼进 next_prompt——于是这条“便签”每轮都被重新贴到模型眼前，长任务也不会忘掉当前重点。任务一结束，self.working 随之消失。

2 长期结晶：do_start_long_term_update 的蒸馏提示词 点击展开
🧪 注入的蒸馏提示
ga.pyGenericAgentHandler.do_start_long_term_update
def do_start_long_term_update(self, args, response):
    prompt = '''### [总结提炼经验] ...
- 环境事实（路径/凭证/配置） → file_patch 更新 L2，同步 L1
- 复杂任务经验（关键坑点/前置条件） → L3 精简 SOP
''' + get_global_memory()
    path = './memory/memory_management_sop.md'
    result = 'This is L0:\n' + file_read(path, show_linenos=False)
    return StepOutcome(result, next_prompt=prompt)
⚙️ 结晶的三个动作

这个工具本身不写记忆，它只是“开启结算”：把 L0 全文作为工具结果回灌，并附上一段蒸馏提示词，引导模型自己用普通文件工具完成三件事——① 环境事实用 file_patch 最小更新 L2、同步 L1 索引；② 复杂任务经验写成 L3 的精简 SOP；③ 无新增内容就跳过。真正动手改文件的是模型，不是这段代码。

❓ 为什么“无行动不记忆”如此重要

模型的“固有知识”和“推理猜测”可能是错的，一旦当事实写进记忆，下次会被当真，错误会复利累积。L0 第 1 条强制：只有工具调用真正成功的结论才配结晶。这条铁律把记忆库守成“越用越准”而不是“越用越脏”，是自进化技能树能被反复信任的根基。

⚠️ 坑点：改记忆要“宁可不改”

L0 第 2 条明确：“记忆修改时请极度小心，尽量不要 overwrite 或 code run，只能少量 patch，改不动宁愿不改。”所以结晶时优先 file_read 看现有内容，再用 file_patch 做最小局部修改，严禁用 code_run 批量重写整个记忆文件——那样极易误删已验证的避坑信息。

🧩 生活类比
像做实验时手边的草稿纸 + 事后的实验记录本：草稿纸（工作便签）随手记当前要点，做完一组就擦；只有真正验证成功的结论，才郑重地誊进永久的记录本（长期记忆）。没验证过的猜测，绝不入册。
✅ 关键要点
  • 两个记忆工具：working_checkpoint（短期、每轮注入）与 start_long_term_update（长期结晶）。
  • 铁律：无行动，不记忆——只结晶经过验证的信息。
  • 写记忆要最小化：优先小 patch，禁存易变状态。
💡 设计亮点
“无行动，不记忆”这条铁律，是 GA 记忆可信的关键。模型的“固有知识”“推理猜测”一律不准当事实写入——只有工具调用真正成功的结论才配结晶成技能。正是这条原则，把记忆库守成了“越用越准”而不是“越用越脏”，也让后面“自进化”长出的技能树根基扎实、可被反复信任。

Layering is just the "bookshelf"; something still has to write onto it. GenericAgent reads and writes memory with two memory tools: a "working notepad" during a task, and a "long-term memory settlement" when a task wraps up. The first prevents forgetting; the second crystallizes experience into skills.

🌍 The Big Picture

Short-term: update_working_checkpoint writes "what the user wants and the key constraints" onto a notepad that is auto-injected every turn, so a long task does not lose its goal along the way. Long-term: start_long_term_update kicks off a "settlement" after a task, writing action-verified environment facts, user preferences and hard-won lessons minimally into L1/L2/L3.

🔬 In the Source
  • Short-term notepad: ga.py: do_update_working_checkpoint writes key_info / related_sop into self.working, then re-injects it via an "anchor prompt" each turn.
  • Long-term settlement: ga.py: do_start_long_term_update injects a distillation prompt that guides minimal file_patch updates to L2 facts, syncs the L1 index, and trims an L3 SOP when needed.
  • Settlement obeys the L0 iron rules: memory/memory_management_sop.md — only record "action-verified" info, never store volatile state, avoid overwrite and prefer small patches.

Why a "notepad"

checkpoint writes key_info / related_sop into self.working (a plain dict, process-level, never persisted). Afterwards every tool's wrap-up calls _get_anchor_prompt(), splicing the working memory plus recent history into next_prompt — so this "note" is re-posted in front of the model every turn, and even long tasks do not forget the current focus. When the task ends, self.working vanishes with it.

def do_start_long_term_update(self, args, response):
    prompt = '''### [Distill experience] ...
- environment facts (paths/creds/config) → file_patch update L2, sync L1
- complex-task experience (pitfalls/preconditions) → L3 trimmed SOP
''' + get_global_memory()
    path = './memory/memory_management_sop.md'

The three crystallization actions

The tool itself writes no memory; it just "opens the settlement": it feeds the full L0 back as a tool result with a distillation prompt, guiding the model to do three things with ordinary file tools — ① minimally update L2 facts via file_patch and sync the L1 index; ② write complex-task experience as a trimmed L3 SOP; ③ skip if there is nothing new. The model, not this code, actually edits the files.

Why "no execution, no memory" matters so much

A model's "inherent knowledge" and "reasoning guesses" can be wrong; once written as facts they are taken as true next time, and errors compound. L0 rule 1 enforces: only conclusions from genuinely successful tool calls deserve to crystallize. This iron rule keeps the store "more accurate the more you use it" rather than "dirtier" — the foundation that makes the self-evolving skill tree repeatedly trustworthy.

Pitfall: when editing memory, "rather not edit"

L0 rule 2 is explicit: "edit memory with extreme care, avoid overwrite or code_run, only small patches, and rather not edit if you cannot." So crystallization prefers file_read to see existing content, then a minimal local file_patch; never bulk-rewrite the whole memory file with code_run — that easily deletes already-verified pitfall notes.

🧩 Analogy
Like doing experiments with a scratch pad at hand plus a lab notebook afterward: the scratch pad (working notepad) jots current points and gets wiped after each batch; only conclusions that were actually verified are carefully transcribed into the permanent notebook (long-term memory). Unverified guesses never make it in.
✅ Key Takeaways
  • Two memory tools: working_checkpoint (short-term, injected each turn) and start_long_term_update (long-term crystallization).
  • The iron rule: no execution, no memory — only crystallize verified information.
  • Write memory minimally: prefer small patches, never store volatile state.
💡 Design Insight
The iron rule "no execution, no memory" is what makes GA's memory trustworthy. A model's "inherent knowledge" and "reasoning guesses" may never be written as facts — only conclusions from genuinely successful tool calls deserve to crystallize into skills. This very principle keeps the memory store "more accurate the more you use it" rather than "dirtier", giving the later "self-evolution" skill tree a solid, repeatedly trustworthy foundation.
