项目全景地图Project Map

在动手读任何一行代码之前，先建立一张地图：仓库里每个文件、每个目录各负责什么。记住一句话——这整个项目就是一颗约 3000 行的种子，其余能力都是它生长出来的。

🌍 宏观理解

GenericAgent 的代码可以按“离大模型有多近”分成几圈：最内圈是循环与内核（agent_loop.py、llmcore.py），向外是装配与工具（agentmain.py、ga.py），再外是记忆与反思（memory/、reflect/），最外圈是给人用的外壳（frontends/、ga_cli/）。读代码时知道自己站在哪一圈，就不会迷路。

四层结构

①agent_loop.py · llmcore.py
最内核。agent_loop.py 是约 100 行的自主循环；llmcore.py 是 LLM 客户端，负责 chat、流式输出与工具调用解析。
②agentmain.py · ga.py
装配层。agentmain.py 把系统提示词、工具 schema、会话与 handler 接到循环上；ga.py 的 GenericAgentHandler 实现 9 个原子工具的 do_<tool> 方法。
③memory/ · reflect/ · plugins/
经验层。memory/ 存放分层记忆与各类 SOP（.md 流程文档）；reflect/ 负责编排（如 goal_mode、scheduler）；plugins/ 通过 hooks 在循环关键点插桩观测。
④frontends/ · ga_cli/ · simphtml.py
外壳层。frontends/ 提供桌面端、TUI、各类 IM 机器人；ga_cli/ 是命令行入口；simphtml.py 是网页 HTML 简化 / token 优化工具——把网页 DOM 压缩成精简内容，供 web_scan/web_execute_js 工具低成本阅读（被 ga.py 调用）。

🔬 源码对应

几条能帮你立刻上手的指认：

  • 循环的心脏在 agent_loop.py: agent_runner_loop；它接收 client、system_prompt、handler、tools_schema 等参数。
  • 接线发生在 agentmain.py，从 assets/tools_schema*.json 读入工具描述，再 agent_runner_loop(...)。
  • 工具实现都是 do_<tool> 方法，集中在 ga.py: GenericAgentHandler，继承自 agent_loop.py: BaseHandler。

❓ 为什么循环和工具要分开放

agent_loop.py 只关心“节奏”——问模型、派发、收结果、决定是否继续；它不知道任何具体工具。工具实现全在 ga.py。这样循环可以保持在约 100 行、长期不变，而工具能随便增删——两者通过一个简单约定（do_<tool> 方法 + StepOutcome 返回值）解耦。

⚙️ 继承关系

ga.py 顶部写着 from agent_loop import BaseHandler, StepOutcome，于是 class GenericAgentHandler(BaseHandler) 继承了循环里那套 dispatch 机制——它只需补上各个 do_<tool> 方法，派发逻辑由父类 BaseHandler.dispatch 提供。换句话说：循环定义“怎么派发”，子类只填“派发到哪”。

⚠️ 一个容易看漏的细节

README/课程常说 max_turns 默认 40——那是 agent_runner_loop 的函数默认值。但真正跑起来时，agentmain.py 显式传入了 max_turns=80。读源码时要区分“默认值”和“调用处实际传的值”。

❓ 为什么用“圈”而不是“层”来想

“圈”强调一个方向感：所有信息最终都为最内圈那次 chat 调用服务。外壳收集用户意图，经验层决定喂什么记忆，装配层组装 prompt 与工具，最后内核把这些交给大模型。遇到一个文件先问“它属于哪一圈、离 LLM 多远”，就能猜到它大概在干什么。

🔀 和“分门别类的功能目录”对比

很多项目按功能平铺目录（api/、utils/、models/…），你得读很多文件才知道主线在哪。GenericAgent 的圈层模型自带一条主线：外圈调内圈，内圈最终落到一次 LLM 调用。这让“从哪开始读”有了唯一答案——从最内圈的 agent_loop.py 读起。

🧩 生活类比

把项目想成一家小餐馆：agent_loop.py 是后厨的出餐节奏，一道接一道；llmcore.py 是会做菜的大厨；ga.py 里的工具是锅碗刀具；memory/ 是大厨积累的菜谱本；而 frontends/ 是前台与菜单，顾客只跟它打交道。

✅ 关键要点
  • 整个项目是一颗 ~3K 行的种子；其余能力都是运行中长出来的。
  • 按“离大模型多近”分四层：内核 → 装配 → 经验 → 外壳。
  • agent_loop.py 是循环，llmcore.py 是大脑，ga.py 是双手，memory/ 是记忆。
  • 迷路时，先问自己：我现在在哪一层？
💡 设计亮点

注意 memory/ 里有大量 .md 文件（SOP），而不是写死的代码。这是刻意的：流程用自然语言沉淀，模型可读、可改、可自我扩充，于是“加一个新技能”往往等于“多写一份 .md”，而不是改框架。把能力放进记忆，而不是放进代码，正是它能自我进化的结构性原因。

Before reading a single line, build a map: what each file and directory in the repo is responsible for. Keep one idea in mind — the whole project is a roughly 3,000-line seed, and everything else grows from it.

🌍 The Big Picture

GenericAgent's code can be read as rings around the LLM. The innermost ring is the loop and core (agent_loop.py, llmcore.py); around it sits assembly and tools (agentmain.py, ga.py); then memory and reflection (memory/, reflect/); and the outermost ring is the human-facing shell (frontends/, ga_cli/). Knowing which ring you stand in keeps you from getting lost.

Four layers

①agent_loop.py · llmcore.py
The innermost core. agent_loop.py is the ~100-line autonomous loop; llmcore.py is the LLM client handling chat, streaming, and tool-call parsing.
②agentmain.py · ga.py
The assembly layer. agentmain.py wires the system prompt, tools schema, session and handler into the loop; ga.py's GenericAgentHandler implements the 9 atomic tools as do_<tool> methods.
③memory/ · reflect/ · plugins/
The experience layer. memory/ holds layered memory and SOPs (.md procedure docs); reflect/ handles orchestration (e.g. goal_mode, scheduler); plugins/ instruments the loop at key points via hooks.
④frontends/ · ga_cli/ · simphtml.py
The shell layer. frontends/ provides the desktop app, TUI and IM bots; ga_cli/ is the command-line entry; simphtml.py is a web HTML simplifier / token optimizer that shrinks a page's DOM into compact content so the web_scan/web_execute_js tools can read pages cheaply (used by ga.py).

🔬 In the Source

A few pointers to get you oriented immediately:

  • The heart of the loop is agent_loop.py: agent_runner_loop; it takes client, system_prompt, handler, tools_schema and more.
  • Wiring happens in agentmain.py, which loads the tool descriptions from assets/tools_schema*.json and then calls agent_runner_loop(...).
  • The tools are all do_<tool> methods, gathered in ga.py: GenericAgentHandler, subclassing agent_loop.py: BaseHandler.

Why split the loop from the tools

agent_loop.py cares only about rhythm — ask the model, dispatch, collect results, decide whether to continue; it knows nothing about any specific tool. Every tool lives in ga.py. That keeps the loop around 100 lines and essentially frozen, while tools come and go freely — the two are decoupled by one simple contract (a do_<tool> method returning a StepOutcome).

The inheritance chain

ga.py opens with from agent_loop import BaseHandler, StepOutcome, so class GenericAgentHandler(BaseHandler) inherits the dispatch machinery from the loop — it only has to supply the individual do_<tool> methods, while routing is provided by BaseHandler.dispatch in the parent. In short: the loop defines how to dispatch; the subclass fills in where to.

An easy detail to miss

The README and lessons often cite max_turns = 40 — that is the function default in agent_runner_loop. At runtime, though, agentmain.py explicitly passes max_turns=80. When reading source, separate "the default" from "the value the call site actually passes".

Why "rings", not just "layers"

"Rings" convey a direction: everything ultimately serves that innermost chat call. The shell gathers user intent, the experience layer decides which memory to feed, the assembly layer builds the prompt and tools, and finally the core hands it all to the LLM. Meet a new file and just ask "which ring, how far from the LLM?" — and you can already guess what it does.

vs a flat feature-folder layout

Many projects lay folders out flat by feature (api/, utils/, models/…) and you must read many files before the main thread emerges. GenericAgent's ring model has a built-in main thread: outer rings call inner ones, and the innermost lands on a single LLM call. That gives "where do I start reading?" one answer — start from the innermost agent_loop.py.

Why is llmcore.py the largest

Intuitively the "loop" should be the most complex, yet agent_loop.py is only ~133 lines. The real bulk sits in llmcore.py (~1068 lines), because it must adapt to many vendors' protocols (native OpenAI, native Claude, various mixins), handle streaming, and parse tool calls. "Thin loop, thick core" is exactly what "outsourcing complexity to the LLM ecosystem" looks like.

🧩 Analogy

Picture a small restaurant: agent_loop.py is the kitchen's service rhythm, plating one dish after another; llmcore.py is the chef who actually cooks; the tools in ga.py are the pots and knives; memory/ is the chef's growing recipe book; and frontends/ is the front desk and menu that customers actually talk to.

✅ Key Takeaways
  • The whole project is a ~3K-line seed; the rest grows at runtime.
  • Read it as four rings by distance from the LLM: core → assembly → experience → shell.
  • agent_loop.py is the loop, llmcore.py the brain, ga.py the hands, memory/ the memory.
  • When lost, first ask: which ring am I in right now?
💡 Design Insight

Notice that memory/ is full of .md files (SOPs) rather than hard-coded logic. This is deliberate: procedures are distilled in natural language the model can read, edit and extend, so "adding a skill" often means "writing one more .md", not changing the framework. Putting capability into memory rather than into code is the structural reason it can self-evolve.
