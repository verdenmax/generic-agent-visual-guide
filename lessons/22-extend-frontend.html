扩展前端 / 接入新 IMExtending Frontends

还记得第 5 课说的“前端只是脸、内核是同一套循环”吗？这一课就把它落到代码：要接入一个新平台，你只需写一层薄薄的适配器，把平台的收发消息接到 GA 的内核上——其余一律复用。

🌍 宏观理解

每个前端文件做的事都一样：① 把平台收到的消息喂给 GA 内核；② 把 GA 的输出发回平台。通用的命令处理、消息装配都集中在 chatapp_common 里复用。需要让多个 Agent 协作时，还有一个 conductor 做编排。

接入一个新平台

1

接内核

from agentmain import GenericAgent

每个 frontends/*app.py 都从这里拿到同一套 Agent 入口。

2

复用通用逻辑

命令（/new、/continue 等）与消息装配走 chatapp_common，不必重写。

3

写平台 I/O

只剩平台特有的收发：监听消息 → 交给内核 → 把回复发回去。

🔬 源码对应
  • 现成范例：frontends/tgapp.py · wechatapp.py · fsapp.py 等，每个都是“接内核 + 平台 I/O”的薄适配器。
  • 共享逻辑在 frontends/chatapp_common.py（命令清单、/new、/continue 的处理都在这里）。
  • 多 Agent 编排在 frontends/conductor.py（FastAPI + WebSocket，import GenericAgent 来管理多个实例；可用 /conductor 触发）。

🔬 深入源码

1 薄适配器骨架：一个最小前端长什么样 点击展开
🧪 最小适配器骨架
frontends/myapp.pyskeleton
from agentmain import GeneraticAgent   # GenericAgent 的别名
agent = GeneraticAgent()

def on_platform_message(chat_id, text):
    dq = agent.put_task(text, source="myapp")   # ① 喂给内核
    while True:
        item = dq.get()
        if "done" in item:
            send_back(chat_id, item["done"])     # ② 发回平台
            break
⚙️ put_task → done 内部怎么走

内核交互只有一条主线：agent.put_task(text, source=...) 返回一个显示队列 dq，前端循环 dq.get() 取流式输出，遇到带 "done" 的项就是最终回复。chatapp_common.py 里的 AgentChatMixin.run_agent 正是这个循环的标准实现（含 ping 保活）。

❓ 为什么类名有两种写法

规范类名是 GenericAgent；agentmain.py 里有一行 GeneraticAgent = GenericAgent 别名，于是大多数 frontends/*app.py（tgapp / wechatapp / fsapp …）写的是 from agentmain import GeneraticAgent，而 conductor.py 用规范名 GenericAgent。两者等价。

2 chatapp_common 到底复用了什么 点击展开
🧪 开箱即用的零件清单
零件作用
AgentChatMixin命令分发 + run_agent 循环

clean_reply / split_text清洗标签、按长度切分消息

⚙️ 命令是怎么分发的

AgentChatMixin.handle_command 统一解析斜杠命令：/stop 调 agent.abort()、/new 重置对话、/continue 列出可恢复会话、/btw 临时插问、/review 走代码审查——前端一行都不用重写，只要继承这个 Mixin。

🔀 真实范例对比

tgapp.py（Telegram）、wechatapp.py（微信）、fsapp.py（飞书）做的都是同一件事：import 内核、复用 chatapp_common、只写各自平台的收发 I/O。差异全在最外圈的平台 SDK，内核与命令逻辑完全共享。

3 conductor.py：让多个 GA 实例协作 点击展开
🧪 它是什么

frontends/conductor.py 是一个 FastAPI + WebSocket 服务（from agentmain import GenericAgent，默认跑在 127.0.0.1:8900）。它有一个总管 Conductor（自己也是一个 GenericAgent），外加一个 SubagentPool 管理若干子 agent 实例。

⚙️ 多实例怎么起、怎么通信

SubagentPool.start_subagent(prompt) 每次 GenericAgent() 新建一个实例、起一个 runner 线程，再 put_task 派活；运行进度通过 /ws WebSocket 广播到前端 conductor.html。REST 面板有 /subagent、/chat、/approval 等。

⚠️ 每个子 agent 都是独立实例

注意 SubagentPool 里每个 SubAgentState 都持有自己的 GenericAgent 对象，互不共享运行态——这与 Incubator“每节点独立记忆”的理念一致：协作靠消息传递，而不是共享内存，避免一个 agent 的状态污染另一个。

🧩 生活类比
像给同一台游戏主机配一个新手柄：主机（内核）和游戏（能力）都不用动，你只要做一个转接头，把新手柄的按键信号翻译成主机认识的格式。接微信、接钉钉，都是在做这种“转接头”，工作量小得惊人。
✅ 关键要点
  • 接新平台 = 写一个薄适配器：from agentmain import GenericAgent + 平台 I/O。
  • 命令与消息装配复用 chatapp_common，不必重写。
  • 要多 Agent 协作，用 conductor.py 编排（/conductor）。
💡 设计亮点
“接一个新前端只要几十行”，是第 5 课界面/内核解耦结出的果。因为内核对“消息从哪来”一无所知，前端就退化成纯粹的 I/O 转接——平台再多，内核一行都不用改。这正是好边界的价值：改动被牢牢锁在最外圈，核心始终稳如磐石。

Remember lesson 5's "the frontend is just a face; the core is the same loop"? This lesson puts that into code: to add a new platform, you only write a thin adapter connecting the platform's message I/O to GA's core — everything else is reused.

🌍 The Big Picture

Every frontend file does the same thing: (1) feed messages the platform receives into GA's core; (2) send GA's output back to the platform. Shared command handling and message assembly live in chatapp_common for reuse. When you need multiple agents to collaborate, there is also a conductor for orchestration.

Wiring a new platform

1

Connect the core

from agentmain import GenericAgent

Every frontends/*app.py gets the same agent entry from here.

2

Reuse common logic

Commands (/new, /continue …) and message assembly go through chatapp_common; no rewriting.

3

Write platform I/O

Only platform-specific I/O remains: listen for messages → hand to the core → send the reply back.

🔬 In the Source
  • Ready examples: frontends/tgapp.py · wechatapp.py · fsapp.py and more, each a thin "core + platform I/O" adapter.
  • Shared logic is in frontends/chatapp_common.py (the command list and the handling of /new, /continue live here).
  • Multi-agent orchestration is in frontends/conductor.py (FastAPI + WebSocket, importing GenericAgent to manage multiple instances; triggerable via /conductor).

How put_task → done works inside

Core interaction has one main line: agent.put_task(text, source=...) returns a display queue dq; the frontend loops dq.get() for streamed output, and an item carrying "done" is the final reply. AgentChatMixin.run_agent in chatapp_common.py is exactly this loop (with keep-alive pings).

Why two class spellings exist

The canonical class is GenericAgent; agentmain.py has a line GeneraticAgent = GenericAgent, so most frontends/*app.py (tgapp / wechatapp / fsapp …) write from agentmain import GeneraticAgent, while conductor.py uses the canonical GenericAgent. They are equivalent.

How commands are dispatched

AgentChatMixin.handle_command parses slash commands centrally: /stop calls agent.abort(), /new resets the conversation, /continue lists resumable sessions, /btw asks a side question, /review runs code review — the frontend rewrites none of it, it just inherits the Mixin.

Real examples compared

tgapp.py (Telegram), wechatapp.py (WeChat) and fsapp.py (Feishu) all do the same thing: import the core, reuse chatapp_common, and write only their own platform I/O. All difference sits in the outermost platform SDK; core and command logic are fully shared.

3 conductor.py: making multiple GA instances collaborate click to expand
What it is

frontends/conductor.py is a FastAPI + WebSocket service (from agentmain import GenericAgent, default 127.0.0.1:8900). It has a master Conductor (itself a GenericAgent) plus a SubagentPool managing several sub-agent instances.

How instances start and talk

SubagentPool.start_subagent(prompt) creates a fresh GenericAgent() each time, spins a runner thread, then put_tasks the work; progress is broadcast to the front-end conductor.html over the /ws WebSocket. REST endpoints include /subagent, /chat, /approval.

Each sub-agent is an independent instance

Note each SubAgentState in SubagentPool holds its own GenericAgent object, sharing no runtime state — consistent with Incubator's "independent memory per node": collaboration is by message passing, not shared memory, so one agent's state cannot pollute another's.

🧩 Analogy
Like adding a new controller to the same game console: the console (core) and games (capabilities) stay untouched; you only make an adapter that translates the new controller's button signals into a format the console understands. Wiring WeChat or DingTalk is exactly making such an "adapter" — surprisingly little work.
✅ Key Takeaways
  • A new platform = a thin adapter: from agentmain import GenericAgent + platform I/O.
  • Commands and message assembly reuse chatapp_common; no rewriting.
  • For multi-agent collaboration, orchestrate with conductor.py (/conductor).
💡 Design Insight
"A new frontend in a few dozen lines" is the fruit of lesson 5's interface/core decoupling. Because the core knows nothing about "where a message comes from", a frontend degenerates into pure I/O adaptation — no matter how many platforms, the core changes not a line. This is the value of good boundaries: change is locked into the outermost ring, while the core stays rock-solid.
