Handler 与工具调度Handler & Tool Dispatch

模型说“我要调 code_run”，这句话怎么变成真正跑起来的代码？答案是 agent_loop.py: BaseHandler.dispatch：它按工具名找到对应的 do_<tool> 方法、执行它、并把结果包成 StepOutcome 交回循环。

🌍 宏观理解

调度的规则简单到只有一句话：工具名 X → 调用方法 do_X。所有工具都是 do_<tool> 方法，集中在 ga.py: GenericAgentHandler（它继承自 BaseHandler）。想加一个新工具？再加一个 do_ 方法就行，循环一行都不用改。

agent_loop.pyBaseHandler.dispatch
def dispatch(self, tool_name, args, response, ...):
    method_name = f"do_{tool_name}"
    if hasattr(self, method_name):
        _hook('tool_before', locals())
        ret = yield from try_call_generator(getattr(self, method_name), args, response)
        _hook('tool_after', locals())
        return ret  # 一个 StepOutcome
    else:
        yield f"未知工具: {tool_name}\n"
        return StepOutcome(None, next_prompt=...)
🔬 源码对应
  • 每个 do_ 方法都是生成器：用 yield 实时吐出给用户看的过程，再 return 一个 StepOutcome 作为结构化结果。
  • 辅助函数 try_call_generator 同时兼容“普通返回”和“生成器”两种写法，让 do_ 方法可繁可简。
  • 调度内置两个钩子点 tool_before / tool_after（详见“钩子与可观测性”一课）；未知工具与 bad_json 也在这里兜底处理。
  • 每轮收尾还会调用 turn_end_callback，把本轮的 response、工具结果与 next_prompt 串起来。

🔬 深入源码

1 逐行读 dispatch：从工具名到 do_ 方法 点击展开
🧪 BaseHandler.dispatch 全文
agent_loop.pyBaseHandler.dispatch
def dispatch(self, tool_name, args, response, index=0, tool_num=1):
    method_name = f'do_{tool_name}'
    if hasattr(self, method_name):
        args['_index'] = index; args['_tool_num'] = tool_num
        _hook('tool_before', locals())
        ret = yield from try_call_generator(getattr(self, method_name), args, response)
        _hook('tool_after', locals())
        return ret
    elif tool_name == 'bad_json':
        return StepOutcome(None, next_prompt=args.get('msg', 'bad_json'), should_exit=False)
    else:
        yield f'未知工具: {tool_name}\n'
        return StepOutcome(None, next_prompt=f'未知工具 {tool_name}', should_exit=False)
⚙️ 走查一遍

① 用 f"do_{tool_name}" 拼出方法名；② hasattr 找得到就执行——先注入 _index/_tool_num 两个内部参数，前后各触发一次 hook，中间用 try_call_generator 调用；③ 找不到方法时，bad_json 与未知工具各有兜底，都返回一个非空 next_prompt 让循环继续而不是崩溃。

⚠️ 坑点：_index / _tool_num 是内部参数

dispatch 会往 args 里塞 _index（这是本轮第几个工具）和 _tool_num（本轮一共几个工具）。do_ 方法用它们做分流——例如 do_code_run 用 _tool_num 平分输出长度上限、用 _index>0 决定是否跳过锚点提示。所有以 _ 开头的键在记账与摘要里都会被过滤掉。

2 “工具即生成器”协议：yield 过程，return StepOutcome 点击展开
🧪 try_call_generator 兼容两种写法
agent_loop.pytry_call_generator
def try_call_generator(func, *args, **kwargs):
    ret = func(*args, **kwargs)
    if hasattr(ret, '__iter__') and not isinstance(ret, (str, bytes, dict, list)):
        ret = yield from ret
    return ret
🧪 一个真实工具长这样
ga.pyGenericAgentHandler.do_code_run
def do_code_run(self, args, response):
    ...
    result = yield from code_run(code, code_type, timeout, cwd, ...)  # yield 实时输出
    next_prompt = self._get_anchor_prompt(skip=args.get('_index', 0) > 0)
    return StepOutcome(result, next_prompt=next_prompt)  # return 结构化结果
❓ 为什么用生成器而不是普通函数

一个 do_ 方法要同时做两件事：把执行过程实时流式展示给用户（如 code_run 边跑边打印），以及把最终结果结构化交回循环。生成器天然适配：yield 负责“过程”，return 负责“结果”。try_call_generator 还允许简单工具直接 return StepOutcome(...) 不写 yield，繁简自由。

3 兜底处理：bad_json、未知工具与 do_no_tool 点击展开
⚙️ 三种异常分支
  • bad_json：模型吐出的 tool_use JSON 解析失败，llmcore 会造一个 MockToolCall('bad_json', {'msg':...})；dispatch 把 msg 当 next_prompt 回灌，让模型重发。
  • 未知工具：模型调了不存在的工具名，dispatch yield 一句提示并回灌，同时循环把 client.last_tools 清空（强制重发工具表）。
  • do_no_tool：这一轮模型没调任何工具，循环造 no_tool → 走到 do_no_tool，由它判断是“完成”还是“空回复/截断要重试”。
🧪 do_no_tool 的判定
ga.pyGenericAgentHandler.do_no_tool
def do_no_tool(self, args, response):
    content = getattr(response, 'content', '') or ''
    if not response or (not content.strip() and not thinking.strip()):
        return self._retry_or_exit('[System] Blank response, regenerate and tooluse')
    # 检测“只有一个大代码块却没调工具”等情况…
    return StepOutcome(response, next_prompt=None)  # next_prompt=None ⇒ 任务完成
🔀 完成 vs 重试

do_no_tool 是“任务该不该结束”的实际裁判：正常情况返回 StepOutcome(response, next_prompt=None)，循环据此判 CURRENT_TASK_DONE；但若发现空回复、流中断、max_tokens 截断，或“一大段代码却没调工具”，它就返回一个非空 next_prompt 把模型拉回来重试，连续 3 次空回复才 should_exit。

4 turn_end_callback：每轮收尾的“缝合” 点击展开
🧪 摘要回填与 DANGER 提示
ga.pyGenericAgentHandler.turn_end_callback
def turn_end_callback(self, response, tool_calls, tool_results, turn, next_prompt, exit_reason):
    rsumm = re.search(r'<summary>(.*?)</summary>', _c, re.DOTALL)
    summary = rsumm.group(1).strip() if rsumm else ...
    self.history_info.append(f'[Agent] {summary}')
    if turn % 7 == 0: next_prompt += '...[DANGER] 禁止无效重试…'
    elif turn % 10 == 0: next_prompt += get_global_memory()
    return next_prompt
⚙️ 它把哪些东西缝在一起

turn_end_callback 在循环每轮末尾被调用，负责：① 从模型回复里抽 <summary> 追加进 history_info（供下轮锚点提示回灌）；② 按 turn 周期插入 DANGER 提示或重灌全局记忆；③ 计划模式下提醒读 plan.md；④ 消费 master 注入的 keyinfo/intervene。它的返回值就是循环写进下一轮 messages 的 next_prompt。

🧩 生活类比
像公司前台的总机转接：你报一个部门名（工具名），总机就把电话接到对应分机（do_ 方法）。前台不需要懂每个部门怎么干活，只要知道“名字 → 分机”的对应关系；新开一个部门，只要登记一个新分机号即可。
✅ 关键要点
  • 调度规则：工具名 X → 方法 do_X，集中在 GenericAgentHandler。
  • do_ 方法是生成器：yield 过程输出，return 一个 StepOutcome。
  • 加工具 = 加一个 do_ 方法；循环与调度无需改动。
💡 设计亮点
“工具即生成器”是这里最优雅的一招：同一个方法既能流式展示执行过程，又能结构化返回最终结果，两件事一次写完。再配上 f"do_{tool_name}" 的约定式调度，整套工具系统对扩展开放、对核心封闭——这正是 GA 能从 9 个工具不断长出新能力的结构基础。

The model says "I want to call code_run" — how does that sentence become real running code? The answer is agent_loop.py: BaseHandler.dispatch: it finds the matching do_<tool> method by tool name, runs it, and wraps the result in a StepOutcome handed back to the loop.

🌍 The Big Picture

The dispatch rule is one sentence: tool name X → call the method do_X. Every tool is a do_<tool> method, gathered in ga.py: GenericAgentHandler (which subclasses BaseHandler). Want a new tool? Add one more do_ method; the loop needs zero changes.

agent_loop.pyBaseHandler.dispatch

    else:
        yield f"unknown tool: {tool_name}\n"
        return StepOutcome(None, next_prompt=...)
🔬 In the Source
  • Each do_ method is a generator: it yields process output for the user in real time, then returns a StepOutcome as the structured result.
  • The helper try_call_generator supports both "plain return" and "generator" styles, so do_ methods can be simple or rich.
  • Dispatch has two built-in hook points, tool_before / tool_after (see the "Hooks & Observability" lesson); unknown tools and bad_json are also handled here.
  • At the end of each turn it also calls turn_end_callback, stitching this turn's response, tool results and next_prompt together.

        _hook('tool_after', locals())

        yield f'unknown tool: {tool_name}\n'
        return StepOutcome(None, next_prompt=f'unknown tool {tool_name}', should_exit=False)
A walkthrough

① build the method name with f"do_{tool_name}"; ② if hasattr finds it, run it — first inject the internal args _index/_tool_num, fire a hook before and after, and call it through try_call_generator; ③ when no method is found, bad_json and unknown tools each have a fallback, both returning a non-empty next_prompt so the loop continues instead of crashing.

Pitfall: _index / _tool_num are internal args

dispatch injects _index (which tool this is in the turn) and _tool_num (how many tools this turn) into args. do_ methods use them to branch — e.g. do_code_run divides the output-length cap by _tool_num and uses _index>0 to decide whether to skip the anchor prompt. Any key starting with _ is filtered out of accounting and summaries.

Why a generator instead of a plain function

A do_ method must do two things at once: stream its progress to the user in real time (e.g. code_run prints as it runs) and hand a structured result back to the loop. A generator fits naturally: yield carries the "progress", return carries the "result". try_call_generator also lets simple tools just return StepOutcome(...) without any yield — rich or simple, your choice.

3 Fallbacks: bad_json, unknown tools, and do_no_tool click to expand
Three fallback branches
  • bad_json: when the model's tool_use JSON fails to parse, llmcore fabricates a MockToolCall('bad_json', {'msg':...}); dispatch feeds the msg back as next_prompt so the model retries.
  • unknown tool: the model calls a non-existent tool name; dispatch yields a note and feeds it back, while the loop clears client.last_tools (forcing a re-send of the tool list).
  • do_no_tool: the model called no tool this turn; the loop fabricates no_tool → reaches do_no_tool, which decides "done" vs "blank/truncated, retry".
do_no_tool decisions
ga.pyGenericAgentHandler.do_no_tool
def do_no_tool(self, args, response):
    content = getattr(response, 'content', '') or ''
    if not response or (not content.strip() and not thinking.strip()):
        return self._retry_or_exit('[System] Blank response, regenerate and tooluse')
    # detect "one big code block but no tool call", etc…
    return StepOutcome(response, next_prompt=None)  # next_prompt=None ⇒ task done
Done vs retry

do_no_tool is the real referee for "should the task end": normally it returns StepOutcome(response, next_prompt=None), on which the loop decides CURRENT_TASK_DONE; but if it spots a blank reply, a broken stream, a max_tokens truncation, or "a big code block but no tool call", it returns a non-empty next_prompt to pull the model back for a retry, only setting should_exit after 3 blank replies in a row.

4 turn_end_callback: stitching up the end of each turn click to expand
Summary backfill and DANGER nudges
ga.pyGenericAgentHandler.turn_end_callback
def turn_end_callback(self, response, tool_calls, tool_results, turn, next_prompt, exit_reason):
    rsumm = re.search(r'<summary>(.*?)</summary>', _c, re.DOTALL)
    summary = rsumm.group(1).strip() if rsumm else ...
    self.history_info.append(f'[Agent] {summary}')
    if turn % 7 == 0: next_prompt += '...[DANGER] no pointless retries…'
    elif turn % 10 == 0: next_prompt += get_global_memory()
    return next_prompt
What it stitches together

turn_end_callback runs at the end of each loop turn and is responsible for: ① extracting <summary> from the model reply and appending it to history_info (re-injected via the next anchor prompt); ② inserting DANGER nudges or re-loading global memory on turn cycles; ③ reminding to read plan.md in plan mode; ④ consuming master-injected keyinfo/intervene. Its return value is exactly the next_prompt the loop writes into the next turn's messages.

🧩 Analogy
Like a company switchboard routing a call: you say a department name (the tool name) and the operator connects you to the right extension (the do_ method). The operator need not know how each department works, only the "name → extension" mapping; opening a new department just means registering one new extension.
✅ Key Takeaways
  • Dispatch rule: tool name X → method do_X, gathered in GenericAgentHandler.
  • do_ methods are generators: yield process output, return a StepOutcome.
  • Adding a tool = adding a do_ method; the loop and dispatch stay untouched.
💡 Design Insight
"A tool is a generator" is the most elegant move here: one method both streams its progress and returns a structured result — both written at once. Combined with the convention-based f"do_{tool_name}" dispatch, the whole tool system is open to extension and closed at the core — the structural basis for GA growing new abilities from just 9 tools.
