输入与移动端Input & Mobile (ADB)

上一课让 Agent “看见”，这一课让它“动手”：在电脑上控制鼠标键盘，在手机上通过 ADB 驱动安卓。看得见、点得到，GA 对设备的控制闭环才算合上。

🌍 宏观理解

两条“手”的通路：在桌面端，ljqCtrl 直接调 Win32 API 移动鼠标、点击、敲键；在移动端，adb_ui 用 ADB / uiautomator2 把安卓界面 dump 出来再操作。它们都和上一课的视觉配合——视觉给坐标，输入去执行。

两条输入通路

桌面：鼠标键盘

ljqCtrl 用 Click(x,y)、SetCursorPos、Press("ctrl+v") 等操作，全程物理坐标，并提供 DPI 安全的窗口截图。

移动：ADB 安卓

adb_ui 优先用 uiautomator2 dump 界面层级（动画密集的 App 更稳），原生 adb 兜底，必要时配合视觉补盲。

🔬 源码对应
  • 桌面输入在 memory/ljqCtrl.py（Click / SetCursorPos / Press / FindBlock / GrabWindow，基于 win32api）；要点见 memory/ljqCtrl_sop.md。
  • 一条硬规矩：始终用物理坐标，且严禁 import pyautogui（会污染 win32api）。
  • 安卓控制在 memory/adb_ui.py（u2 优先、原生 adb fallback，dump 配合 ui_detect 补盲）；背景见 memory/computer_use.md。

⚙️ dpi_scale 怎么换算

加载时它用 GDI 的 DESKTOPHORZRES（物理分辨率）除以 SM_CXSCREEN（逻辑分辨率）算出 dpi_scale，满足 Logical = Physical × dpi_scale。你传物理坐标，SetCursorPos 内部再乘 dpi_scale 转成系统要的逻辑坐标——所以调用方永远只想物理坐标。

⚠️ 严禁 import pyautogui

文件头第一行就是大写警告：禁止在此工具链 import pyautogui。pyautogui 会改动 win32 的 DPI 感知 / 坐标语义，和 ljqCtrl 的物理坐标体系冲突，导致点击全部错位。这是一条硬规矩，不是建议。

2 Click(check=True)：点完自动验证 点击展开
⚙️ 内部怎么走

Click 默认 check=True：点击前用 ScreenCapAt(x,y) 抓点击点周边一小块、并记下当前前台窗口；点击后等 0.5s 再抓一次，比较两张图有多少像素变了，同时检测前台窗口是否切换，并打印 [Click check] N/total px changed | fg: ...。

❓ 为什么要验证

盲点击是自动化最大的不可靠来源——点空了、点偏了、窗口没响应，脚本却以为成功了。把“点击是否真的产生了变化”做进 Click 的返回值，Agent 就能立刻看出点击有没有生效，失败时换坐标重试，而不是一路错下去。

3 安卓控制：adb_ui 的 dump 与补盲 点击展开
⚙️ u2 优先、native 兜底

ui() 先试 _dump_u2()（uiautomator2，不受 idle 限制，适合美团这种动画密集 App），失败再 _dump_native()（原生 uiautomator dump，需界面静止）；拿到 XML 后 _parse_xml 解析出每个节点的 text / clickable / 中心坐标 (cx,cy)。

🧪 点击与节点

定位到节点后用 tap(x,y)（底层 adb shell input tap）点过去。弹窗检测的小技巧也写在文件头：ui(clickable_only=True, raw=True) 找全屏 FrameLayout + 底部小 ImageView（关闭 X）。

⚠️ 已知包名与中文输入

文件头预存了已知包名（美团外卖 com.sankuai.meituan.takeoutnew、淘宝 com.taobao.taobao）省去查找。一个坑：别硬啃 adb 中文输入，搜索框一般直接打拼音/首字母即可；遇到小程序等 dump 不全的界面，再叠加上一课的 ui_detect 视觉补盲。

🧩 生活类比
如果说视觉是“眼睛”，这一课就是“手”：电脑上的手是鼠标和键盘，手机上的手是隔空操作的遥控器（ADB）。眼睛找到“发送按钮在哪”，手负责真的把它按下去——缺一不可。
✅ 关键要点
  • 桌面用 ljqCtrl（win32api）做鼠标键盘；移动用 adb_ui（u2/adb）控安卓。
  • 始终物理坐标；桌面端严禁 import pyautogui。
  • 输入与视觉配合：视觉给坐标，输入去点击/敲键。
💡 设计亮点
把“手”做成最底层、最通用的能力，是 GA 强执行力的根。它不依赖某个 App 开放接口，而是回到人类操作设备的最小公分母——点、敲、滑。于是“订杯奶茶”“群发微信”“驱动支付宝”这些任务，本质上都被还原成了“看一眼 + 点几下”，用同一套手在真实设备上完成。

The last lesson let the agent "see"; this one lets it "act": on a computer it controls the mouse and keyboard, and on a phone it drives Android over ADB. Seeing plus touching closes GA's control loop over a device.

🌍 The Big Picture

Two "hand" paths: on the desktop, ljqCtrl calls Win32 APIs directly to move the mouse, click and type; on mobile, adb_ui uses ADB / uiautomator2 to dump and drive the Android UI. Both pair with the previous lesson's vision — vision gives coordinates, input carries them out.

Two input paths

Desktop: mouse & keyboard

ljqCtrl uses Click(x,y), SetCursorPos, Press("ctrl+v") and more, all in physical coordinates, plus DPI-safe window capture.

Mobile: ADB Android

adb_ui prefers uiautomator2 to dump the UI hierarchy (steadier for animation-heavy apps), with native adb as fallback, aided by vision when needed.

🔬 In the Source
  • Desktop input is in memory/ljqCtrl.py (Click / SetCursorPos / Press / FindBlock / GrabWindow, on win32api); the playbook is memory/ljqCtrl_sop.md.
  • A hard rule: always use physical coordinates, and never import pyautogui (it pollutes win32api).
  • Android control is in memory/adb_ui.py (u2 first, native adb fallback, dump combined with ui_detect to fill gaps); background in memory/computer_use.md.

How dpi_scale converts

On load it computes dpi_scale by dividing GDI's DESKTOPHORZRES (physical resolution) by SM_CXSCREEN (logical resolution), satisfying Logical = Physical × dpi_scale. You pass physical coordinates and SetCursorPos multiplies by dpi_scale internally to the logical coordinates the OS wants — so callers only ever think in physical coordinates.

Never import pyautogui

The very first line of the file is an upper-case warning: do not import pyautogui in this toolchain. pyautogui alters win32's DPI awareness / coordinate semantics, clashing with ljqCtrl's physical-coordinate system and throwing every click off. It is a hard rule, not a suggestion.

2 Click(check=True): self-verify after the click click to expand
How it works inside

Click defaults to check=True: before clicking it grabs a small patch around the point with ScreenCapAt(x,y) and records the current foreground window; after clicking it waits 0.5s, grabs again, compares how many pixels changed, also checks whether the foreground window switched, and prints [Click check] N/total px changed | fg: ....

Why verify at all

Blind clicking is the biggest source of automation flakiness — a miss, an off-by-a-bit, an unresponsive window, yet the script assumes success. By baking "did the click actually change anything" into Click's return value, the agent can tell immediately whether the click landed and retry with new coordinates on failure instead of compounding the error.

3 Android control: adb_ui's dump and gap-filling click to expand
u2 first, native fallback

ui() first tries _dump_u2() (uiautomator2, not bound by idle state, good for animation-heavy apps like Meituan), then falls back to _dump_native() (native uiautomator dump, which needs a still UI); from the XML, _parse_xml extracts each node's text / clickable / center (cx,cy).

Tapping and nodes

Once a node is located, tap it with tap(x,y) (backed by adb shell input tap). A popup-detection trick is noted in the file header too: ui(clickable_only=True, raw=True) finds a full-screen FrameLayout plus a small bottom ImageView (the close X).

Known packages and Chinese input

The header pre-stores known package names (Meituan delivery com.sankuai.meituan.takeoutnew, Taobao com.taobao.taobao) to skip lookups. One pitfall: do not fight adb Chinese input — a search box usually accepts pinyin/initials directly; for mini-programs and other under-dumped UIs, layer on the previous lesson's ui_detect vision to fill the gaps.

🧩 Analogy
If vision is the "eyes", this lesson is the "hands": on a computer the hand is the mouse and keyboard; on a phone it is a remote control acting at a distance (ADB). The eyes find "where the Send button is", the hands actually press it — neither works alone.
✅ Key Takeaways
  • Desktop uses ljqCtrl (win32api) for mouse/keyboard; mobile uses adb_ui (u2/adb) to drive Android.
  • Always physical coordinates; never import pyautogui on the desktop.
  • Input pairs with vision: vision gives coordinates, input clicks/types.
💡 Design Insight
Making the "hands" the lowest-level, most general capability is the root of GA's strong execution. It does not depend on any app exposing an API; it falls back to the lowest common denominator of how humans operate devices — tap, type, swipe. So tasks like "order a milk tea", "mass-send WeChat", "drive Alipay" all reduce to "glance + a few taps", done by the same hands on real devices.
