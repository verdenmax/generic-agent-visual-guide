端到端实战：造一个新技能End-to-End: Build a Skill

理论讲完了，来走一遍真实流程。以一句“帮我读一下微信聊天记录”为例，看 GA 第一次怎么从零摸索，又怎么把成果沉淀成一条技能，让第二次变成一句话的事。

🌍 宏观理解

“造技能”不是单独的功能，而是把前面所有零件拼起来用一次：用工具去探索，用记忆去结晶。关键分水岭就一个——第一次（慢，要试错）和之后每次（快，直接召回）。

第一次：从零摸索

1

记住目标

收到任务，先用 update_working_checkpoint 记下“要读微信记录”和关键约束。

2

探索与试错

用 code_run 装依赖、定位数据库、写读取脚本，失败就读报错再改。

3

验证成功

真正跑通、读出消息——这一步是“能不能记忆”的前提（无行动，不记忆）。

4

结晶为技能

start_long_term_update：把脚本路径与关键坑点写成 L3 SOP，在 L1 索引登记一行。

之后每次：一句话

你说的话第一次之后每次
“读我的微信记录”装依赖 → 逆向数据库 → 写读取脚本 → 存为技能一句话直接调用
“盯盘并提醒我”装行情库 → 搭选股流程 → 配定时 → 存为技能一句话启动
🔬 源码对应
  • 用到的工具都来自第 7 课：code_run（探索）、file_write / file_patch（写脚本与 SOP）、update_working_checkpoint 与 start_long_term_update（记忆）。
  • 结晶遵循 L0 记忆铁律（memory/memory_management_sop.md）：只记验证成功的要点，最小化 patch；技能落到 L3（memory/ 下的 *_sop.md）。
  • 下次靠 memory/skill_search/ 在技能库里找回这条 SOP。

⚙️ update_working_checkpoint 和 start_long_term_update 有什么区别

前者是短期工作记忆：在任务进行中记下“我现在要干嘛、关键约束是什么”，用完即弃；后者是长期结晶：任务成功后把可复用经验沉淀成 L3 SOP。一个管“当下别走神”，一个管“以后还能用”。

⚠️ 为什么第③步不能省

“无行动，不记忆”：必须真的跑通、读出消息，才允许进入第④步结晶。略过验证直接保存，等于把没跑通的脚本当成技能存进去，下次召回反而误事。

⚙️ 召回路径

你再说“读微信记录”，GA 不再从零探索：先用 memory/skill_search/ 语义检索命中那条 SOP，顺着 L1 索引指针打开 L3 的 *_sop.md，照着里面的脚本路径与命令一步到位。

🔀 第一次 vs 之后每次

第一次：装依赖 → 逆向数据库 → 写脚本 → 验证 → 结晶，可能折腾很久；之后每次：一句话直接调用。差别不在“模型更聪明了”，而在经验被留下了——同类任务越做越快、越做越省。

❓ 为什么“没有新东西”反而是优点

正因为每块积木都小而正交、可自由拼接，“造技能”才不需要额外发明任何机制。与其堆功能，不如把少数几件事做对，再让它们组合长出无穷——这是 GA 最深的设计取向。

⚠️ 常见误解

很多人以为“学会新技能”需要装插件、改框架代码。在 GA 里完全不用：技能只是 memory/ 下多出来的一个 *_sop.md，加上 L1 索引里多出的一行——种子代码一行没动。

🧩 生活类比
像第一次去一个陌生小区送货：你得边问边找、走几条冤枉路；但只要这一趟真送到了，你就把“几号门、哪个单元、门禁密码”记进备忘。第二趟，导航直达，再不绕路。GA 的“造技能”就是把这本送货备忘自动写下来。
✅ 关键要点
  • 第一次：记目标 → 探索试错 → 验证成功 → 结晶为技能。
  • 之后每次：顺着技能库一句话召回，不再重复试错。
  • 全程没有新机制，只是把工具 + 记忆按自进化闭环用了一遍。
💡 设计亮点
注意这一课没有引入任何新东西：工具是第 7 课的、记忆是第 11–12 课的、闭环是第 20 课的。“造技能”之所以成立，正因为前面每块积木都小而正交、能自由拼接。这就是 GenericAgent 最深的设计取向——与其堆功能，不如把少数几件事做对，然后让它们互相组合，长出无穷。

Enough theory — let us walk a real flow. Take "read my WeChat messages" as an example, and watch how GA fumbles from scratch the first time, then settles the result into a skill so the second time becomes a one-liner.

🌍 The Big Picture

"Building a skill" is not a separate feature; it is using all the earlier parts together once: tools to explore, memory to crystallize. The watershed is a single one — the first time (slow, trial and error) versus every time after (fast, direct recall).

First time: from scratch

1

Capture the goal

On receiving the task, use update_working_checkpoint to note "read WeChat messages" and key constraints.

2

Explore & iterate

Use code_run to install deps, locate the database, write a read script; on failure, read the error and fix.

3

Verify success

Actually run it and read out the messages — the prerequisite for "may we remember" (no execution, no memory).

4

Crystallize a skill

start_long_term_update: write the script path and key pitfalls into an L3 SOP, and register one line in the L1 index.

Every time after: one sentence

🔬 In the Source
  • The tools used are all from lesson 7: code_run (explore), file_write / file_patch (write scripts and SOPs), update_working_checkpoint and start_long_term_update (memory).
  • Crystallization follows the L0 memory rules (memory/memory_management_sop.md): record only verified essentials, patch minimally; the skill lands in L3 (a *_sop.md under memory/).
  • Next time, memory/skill_search/ finds this SOP back in the skill library.

update_working_checkpoint vs start_long_term_update

The former is short-term working memory: mid-task, note "what I am doing now and the key constraints", discarded when done. The latter is long-term crystallization: after success, settle reusable experience into an L3 SOP. One keeps the agent on-task now; the other makes it reusable later.

Why step ③ cannot be skipped

"No action, no memory": the script must actually run and read out messages before step ④ may crystallize. Skipping verification and saving anyway stores an unproven script as a skill — which then misfires on recall.

2 Every time after: how one sentence gets recalled click to expand
The recall path

When you say "read WeChat messages" again, GA no longer explores from scratch: it semantically matches the SOP via memory/skill_search/, follows the L1 index pointer to open the L3 *_sop.md, and executes its script path and commands in one shot.

First time vs every time after

First time: install deps → reverse DB → write script → verify → crystallize, possibly a long fiddle. After: one-line invoke. The difference is not "a smarter model" but experience kept — similar tasks get faster and cheaper each time.

Why "nothing new" is a strength

Precisely because every block is small, orthogonal and freely composable, "building a skill" needs no extra machinery. Rather than piling on features, get a few things right and let them combine without end — GA's deepest design orientation.

A common misconception

Many assume "learning a new skill" needs plugins or framework edits. In GA it needs neither: a skill is just one more *_sop.md under memory/ plus one more line in the L1 index — the seed code is untouched.

🧩 Analogy
Like delivering to an unfamiliar neighborhood for the first time: you ask around and take a few wrong turns; but once this trip actually succeeds, you note "which gate, which unit, the door code". The second trip, navigation takes you straight there. GA's "build a skill" simply writes that delivery note down automatically.
✅ Key Takeaways
  • First time: capture goal → explore & iterate → verify success → crystallize a skill.
  • Every time after: recall from the skill library in one sentence, no repeated trial and error.
  • No new mechanism throughout — just tools + memory used once along the self-evolution loop.
💡 Design Insight
Notice this lesson introduces nothing new: the tools are from lesson 7, the memory from lessons 11–12, the loop from lesson 20. "Build a skill" holds together precisely because every earlier block is small, orthogonal and freely composable. This is GenericAgent's deepest design orientation — rather than piling on features, get a few things right and let them combine to grow without end.
