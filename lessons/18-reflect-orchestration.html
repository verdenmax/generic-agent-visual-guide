反思与编排Reflection & Orchestration

前面的循环是“你说一句、它做一段”。但要让 Agent 自己持续推进、按目标自驱、甚至多个 worker 协作，就需要一层反思（reflect）机制：在循环之外，定时“探一探、推一把”。

🌍 宏观理解

reflect/ 下的每个模块都是一个可插拔的定时探针：它有自己的检查间隔，每隔一段时间运行 check()——如果发现“该干活了”，就返回一段提示词去唤醒 Agent，否则返回 None 保持安静。不同模块对应不同的编排玩法。

几种编排模块

模块玩法
goal_mode.py目标模式：按一份 state 持续自驱，直到预算耗尽。
scheduler.py调度器：类 cron 的定时任务（带端口锁防重复启动）。
checklist_master.py清单主控：轮询一个清单/看板，逐项推进。
agent_team_worker.py团队 worker：从共享 BBS 接单，多 Agent 协作。
🔬 源码对应
  • 反思模块由 agentmain.py --reflect reflect/<module>.py 启动；每个模块约定有 INTERVAL、init(a)、check() 三样东西。
  • check() 的返回值就是“唤醒提示”：返回字符串 → 注入并唤醒 Agent；返回 None → 本次跳过。
  • goal_mode 读 GOAL_STATE 指定的 state json；scheduler 用一个端口锁（127.0.0.1:45762）防止重复启动；agent_team_worker 预检 BBS（见 assets/agent_bbs.py）。

⚙️ agentmain 怎么驱动

用 agentmain.py --reflect reflect/<module>.py 启动后，主程序动态 import 该模块，有 init(a) 就先调（把 --key value 风格的额外参数传进去），然后进一个循环：每隔 INTERVAL 秒调一次 check()，返回非空就 put_task(task, source='reflect') 注入 Agent。

⚙️ 热重载

agentmain 记下脚本的 mtime，每轮检查文件是否被改动；改了就 exec_module 重新加载并再调 init。于是你可以边跑边改反思逻辑，不必重启 Agent。

2 goal_mode：按预算自驱到底 点击展开
⚙️ state 与预算

goal_mode.py 的 INTERVAL=3（跑完立刻再检查）。它读 GOAL_STATE 指向的 json，里面有 objective、start_time、budget_seconds、turns_used / max_turns。每轮算出已用/剩余时间，回一段续推提示并把 turn +1。

🧪 两种提示

预算未尽返回 CONTINUATION_PROMPT（“禁止说已完成是否继续，没到预算不准停”）；remaining<=0 或 turn>max_turns 时返回 BUDGET_LIMIT_PROMPT 做最后一轮收口，再返回 /exit 结束。

❓ 为什么禁止“提前交付”

模型天然倾向于尽快说“做完了”。Goal Mode 反过来逼它把时间预算花满：每轮换一个角度（测试/边界/性能/安全/美观）持续打磨同一个核心成果，从而把“能用”磨成“好用”。

3 scheduler 的端口锁与多模块对比 点击展开
⚙️ 端口锁防重复启动

scheduler.py 在模块顶层 bind('127.0.0.1', 45762)：若已有一个调度器在跑，第二次 bind 会失败让 agentmain 直接崩退，保证全机只有一个调度器。用 try: _lock except NameError 守护，热重载时跳过重复绑定。

🧪 repeat 冷却

它扫 sche_tasks/ 下的任务，按 _parse_cooldown(repeat) 把 daily/weekly/monthly/every_2h 等折算成冷却时间（略短于周期防漂移），到点未做且在 DEFAULT_MAX_DELAY 窗口内才触发，做完归档到 sche_tasks/done。

🔀 看板 vs 接单

checklist_master.py 轮询一份 state.json（可挂一个 BBS 做 mapreduce），逐项派活；agent_team_worker.py 则是 worker 端，check() 内预检 BBS（/posts?limit=10），无新帖返回 None 不唤醒，有新帖才回一段“接单—执行—汇报”的提示。BBS 服务本体见 assets/agent_bbs.py。

🧩 生活类比
像给一个埋头干活的工人配了几位不同的工头：目标工头盯着“这件事没做完就别停”，排班工头按点喊“到时间了，去做那件事”，看板工头盯着任务清单逐条派活，接单工头则去公告栏揽活。工人（Agent 循环）还是那个工人，是工头们决定了他何时、为何再次动起来。
✅ 关键要点
  • reflect/ 模块是循环之外的定时探针，用 check() 决定是否唤醒 Agent。
  • 四种玩法：目标自驱、定时调度、清单主控、团队接单。
  • 用 agentmain.py --reflect 启动；约定 INTERVAL / init / check。
💡 设计亮点
编排没有被塞进核心循环，而是抽成一层统一约定的探针：所有花样——自驱、定时、看板、协作——都被归一成同一个问题“check() 这次要不要唤醒、用什么提示唤醒”。于是“加一种新编排”=“写一个新 reflect 模块”，内核依旧是那 100 行。复杂的多 Agent 行为，由简单的探针组合而成。

The loop so far is "you say something, it does a chunk". But to make the agent keep going on its own, self-drive toward a goal, or even have multiple workers collaborate, you need a layer of reflection: outside the loop, periodically "check and nudge".

🌍 The Big Picture

Each module under reflect/ is a pluggable periodic probe: it has its own check interval and runs check() every so often — if it finds "time to act", it returns a prompt that wakes the agent, otherwise it returns None and stays quiet. Different modules map to different orchestration styles.

A few orchestration modules

ModuleStyle
goal_mode.pyGoal mode: keep self-driving from a state file until the budget runs out.
scheduler.pyScheduler: cron-like timed tasks (with a port lock to prevent double-start).
checklist_master.pyChecklist master: poll a checklist/board and advance items one by one.
agent_team_worker.pyTeam worker: pick up jobs from a shared BBS for multi-agent collaboration.
🔬 In the Source
  • Reflection modules are launched by agentmain.py --reflect reflect/<module>.py; each module conventionally has INTERVAL, init(a) and check().
  • The return value of check() is the "wake prompt": return a string → inject and wake the agent; return None → skip this round.
  • goal_mode reads GOAL_STATE a state json pointed to by GOAL_STATE; scheduler uses a port lock (127.0.0.1:45762) to prevent double-start; agent_team_worker pre-checks a BBS (see assets/agent_bbs.py).

The minimal skeleton

INTERVAL = 1800      # seconds between checks
ONCE = False

def check():
    # return str = wake prompt; return None = skip
    return '[AUTO]...'
How agentmain drives it

Launched via agentmain.py --reflect reflect/<module>.py, the main program dynamically imports the module, calls init(a) first if present (passing in extra --key value-style args), then loops: every INTERVAL seconds it calls check(), and on a non-empty return it injects the agent via put_task(task, source='reflect').

Hot reload

agentmain records the script's mtime and checks each round whether the file changed; if so it exec_modules to reload and calls init again. So you can edit the reflection logic while it runs without restarting the agent.

2 goal_mode: self-drive to the budget's end click to expand
State and budget

goal_mode.py uses INTERVAL=3 (re-check the moment a run finishes). It reads the json pointed to by GOAL_STATE, holding objective, start_time, budget_seconds and turns_used / max_turns. Each round it computes elapsed/remaining time, returns a continuation prompt and increments the turn.

Two prompts

While budget remains it returns CONTINUATION_PROMPT ("do not say done/continue, do not stop before the budget"); when remaining<=0 or turn>max_turns it returns BUDGET_LIMIT_PROMPT for a final wrap-up round, then returns /exit to finish.

Why forbid "early delivery"

Models naturally tend to declare "done" as soon as possible. Goal Mode instead forces them to spend the whole time budget: each round take a different angle (tests/edge cases/performance/security/polish) to keep refining the same core deliverable, turning "works" into "works well".

3 scheduler's port lock and a module comparison click to expand
Port lock prevents double-start

scheduler.py does a module-top bind('127.0.0.1', 45762): if a scheduler is already running, the second bind fails and crashes agentmain out, guaranteeing exactly one scheduler per machine. A try: _lock except NameError guard skips re-binding on hot reload.

repeat cooldowns

It scans tasks under sche_tasks/ and uses _parse_cooldown(repeat) to convert daily/weekly/monthly/every_2h into cooldowns (slightly shorter than the period to avoid drift); it fires only when due, undone, and within the DEFAULT_MAX_DELAY window, archiving finished runs to sche_tasks/done.

Board vs job-board

checklist_master.py polls a state.json (which may attach a BBS for mapreduce) and assigns items; agent_team_worker.py is the worker side, whose check() pre-checks the BBS (/posts?limit=10), returns None to skip when there is nothing new, and only on a new post returns a "claim — execute — report" prompt. The BBS service itself is assets/agent_bbs.py.

🧩 Analogy
Like giving a heads-down worker several different foremen: the goal foreman insists "do not stop until this is done", the scheduling foreman calls "it is time, go do that", the board foreman assigns items off a checklist, and the job-board foreman picks up postings. The worker (the agent loop) is the same worker; the foremen decide when and why he starts moving again.
✅ Key Takeaways
  • reflect/ modules are periodic probes outside the loop; check() decides whether to wake the agent.
  • Four styles: goal self-drive, timed scheduling, checklist master, team job-board.
  • Launched via agentmain.py --reflect; the convention is INTERVAL / init / check.
💡 Design Insight
Orchestration is not stuffed into the core loop but abstracted into a layer of uniformly-agreed probes: every style — self-drive, scheduling, boards, collaboration — reduces to the same question, "should check() wake it this time, and with what prompt". So "add a new orchestration" = "write a new reflect module", while the core stays 100 lines. Complex multi-agent behavior is composed from simple probes.
