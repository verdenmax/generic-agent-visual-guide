长期自治与定时任务Long-Horizon Autonomy

把上一课的“反思探针”用到极致，就得到一个能无人值守、长期运行的 Agent：你离开后它自己找事做，到点了它自己执行，盯着一个目标它能跑上几小时甚至几天。这一课讲 GA 的长期自治。

🌍 宏观理解

长期自治 = 触发 + 自驱 + 留痕。触发可以是“用户离开很久了”或“到点了”；自驱让它读自动化 SOP 持续做事；留痕则靠分层记忆把每段经历沉淀下来，供以后回溯。这三件事都搭在上一课那套 reflect 探针上。

自治是怎么触发的

1

探针周期检查

如 autonomous.py 每隔 30 分钟检查一次。

2

满足条件 → 唤醒

检测到“用户离开超过 30 分钟”，返回一句自治提示唤醒 Agent。

3

读 SOP 自驱

Agent 按 autonomous_operation_sop 持续执行自动任务。

4

留痕 / 结算

过程写入工作便签，重要经验结晶进长期记忆，会话归入 L4。

🔬 源码对应
  • 最简单的自治探针：reflect/autonomous.py（INTERVAL=1800 即 30 分钟，check() 返回 “用户离开超过 30 分钟，请执行自动任务”）。
  • 定时任务由 reflect/scheduler.py 驱动；玩法记在 memory/scheduled_task_sop.md。
  • 自治与监督的规范见 memory/autonomous_operation_sop.md 与 memory/supervisor_sop.md；可用 /autorun 进入自主模式（见“斜杠命令”一课）。

🧪 真实源码
reflect/autonomous.py全文（仅 6 行）
# reflect/autonomous.py
INTERVAL = 1800
ONCE = False

def check():
    return "[AUTO]🤖 用户已经离开超过30分钟，作为自主智能体，请阅读自动化sop，执行自动任务。"
⚙️ 它“无条件”唤醒？

注意：这个 check() 每次都返回那句提示，本身不判断“用户是否真的离开”。真正的“离开 30 分钟”是靠 INTERVAL=1800 这个节拍体现的——每 30 分钟唤醒一次；而“是否该自治”交给 Agent 读 SOP 后自行判断。这正是 GA 的风格：探针只管节拍，判断交给模型。

🔀 和 scheduler 的分工

autonomous.py 管“闲时找事做”（粗节拍、无具体任务）；scheduler.py 管“到点做特定事”（细任务、带 repeat 冷却与归档）。两者都是 reflect 探针，一个负责填满空闲，一个负责守住日程。

2 触发 → 自驱 → 留痕的闭环 点击展开
⚙️ 一圈怎么转

① 探针按 INTERVAL 周期 check()；② 返回提示 → put_task(source='reflect') 唤醒 Agent；③ Agent 读 autonomous_operation_sop.md 自驱执行；④ 过程写工作便签、重要经验结晶进长期记忆、会话归入 L4。下一个 INTERVAL 再转一圈。

❓ 为什么没有新内核

“长期自治”听起来很高级，但它没有引入任何新机制——只是把反思探针（何时动）+ SOP（做什么）+ 分层记忆（别忘别重复）三块旧积木拼起来。这也解释了为什么 3K 行种子能长出复杂行为：靠组合，不靠堆叠。

🔀 /autorun vs --reflect

--reflect reflect/autonomous.py 是外部进程挂探针的长跑方式；/autorun 则是会话内一条斜杠命令，让当前 Agent 就地进入自主模式（详见“斜杠命令”一课）。前者适合无人值守的长期部署，后者适合你在对话里临时放手。

⚠️ 自治不是放任

自治模式下 Agent 会真的动手改文件、点界面，所以 supervisor_sop.md 很关键：它划出边界、要求留痕与可回溯，避免“无人时跑偏”。配合分层记忆的 L4 归档，事后能完整复盘每一步。

🧩 生活类比
像一个尽职的夜班值守：你下班走了，它不闲着——按巡检表定时转一圈，发现该处理的就处理，处理完在交接本上记一笔。第二天你回来，事办了，记录也都在。它不需要你一直盯着，因为“何时该动、该做什么、做完记什么”早已写进流程。

💡 设计亮点
看似高级的“长期自治”，其实没有引入任何新内核——它只是把反思探针 + 分层记忆 + SOP 三块旧积木拼起来：探针负责“何时动”，SOP 负责“做什么”，记忆负责“别忘了、别重复”。GA 的复杂能力几乎都是这样由简单件组合而来，而不是堆叠新机制——这正是“3K 行种子代码”能长出参天大树的秘密。

Push the previous lesson's "reflection probes" to the extreme and you get an agent that runs unattended, for the long haul: it finds work after you leave, executes on schedule, and can chase a goal for hours or even days. This lesson covers GA's long-horizon autonomy.

🌍 The Big Picture

Long-horizon autonomy = trigger + self-drive + trace. The trigger can be "the user has been away a while" or "it is time"; self-drive has it read an automation SOP and keep working; tracing relies on layered memory to settle each episode for later recall. All three sit on the previous lesson's reflect probes.

How autonomy gets triggered

1

Probe checks periodically

e.g. autonomous.py checks every 30 minutes.

2

Condition met → wake

On detecting "user away for over 30 minutes", it returns an autonomy prompt to wake the agent.

3

Read SOP, self-drive

The agent keeps running automated tasks per autonomous_operation_sop.

4

Trace / settle

Progress goes to the working notepad, key lessons crystallize into long-term memory, sessions archive to L4.

🔬 In the Source
  • The simplest autonomy probe: reflect/autonomous.py (INTERVAL=1800, i.e. 30 minutes; check() returns "the user has been away for over 30 minutes, run autonomous tasks").
  • Scheduled tasks are driven by reflect/scheduler.py; the playbook is in memory/scheduled_task_sop.md.
  • Autonomy and supervision rules are in memory/autonomous_operation_sop.md and memory/supervisor_sop.md; enter autonomous mode with /autorun (see the "slash commands" lesson).

🔬 Deep Dive

1 autonomous.py in full: the minimal autonomy probe click to expand
The real source
reflect/autonomous.pywhole file (just 6 lines)
# reflect/autonomous.py
INTERVAL = 1800
ONCE = False

def check():
    return "[AUTO]🤖 User away >30 min — as an autonomous agent, read the automation SOP and run autonomous tasks."
Does it wake unconditionally?

Note: this check() returns that prompt every time; it does not itself test "is the user really away". The actual "away for 30 minutes" is expressed by the INTERVAL=1800 cadence — it wakes once every 30 minutes — while "should I act autonomously" is left to the agent after it reads the SOP. Very GA in style: the probe owns the cadence, judgment is left to the model.

Division of labor with scheduler

autonomous.py handles "find work when idle" (coarse cadence, no specific task); scheduler.py handles "do a specific thing on time" (concrete tasks, with repeat cooldowns and archiving). Both are reflect probes — one fills idle time, the other keeps the schedule.

2 The trigger → self-drive → trace loop click to expand
How one cycle turns

(1) the probe runs check() on its INTERVAL; (2) a returned prompt wakes the agent via put_task(source='reflect'); (3) the agent reads autonomous_operation_sop.md and self-drives; (4) progress goes to the working notepad, key lessons crystallize into long-term memory, the session archives to L4. The next INTERVAL turns the loop again.

Why there is no new core

"Long-horizon autonomy" sounds advanced, yet it introduces no new mechanism — it just snaps together three old blocks: reflection probes (when to act) + SOPs (what to do) + layered memory (do not forget or repeat). That is why a 3K-line seed can grow complex behavior: by composition, not accretion.

/autorun vs --reflect

--reflect reflect/autonomous.py is the long-running way to attach a probe as an external process; /autorun is an in-session slash command that puts the current agent into autonomous mode in place (see the "slash commands" lesson). The former suits unattended long-term deployment, the latter suits letting go mid-conversation.

Autonomy is not a free-for-all

In autonomous mode the agent really edits files and clicks UIs, so supervisor_sop.md matters: it draws boundaries and demands traceability, preventing "drift while unattended". Together with layered memory's L4 archiving, every step can be fully reviewed afterward.

🧩 Analogy
Like a conscientious night-shift attendant: you clock out and leave, but it does not idle — it makes timed rounds per a checklist, handles whatever needs handling, and jots it in the handover log. You return the next day to find the work done and the records there. It does not need you watching, because "when to act, what to do, what to log" is already written into the procedure.
✅ Key Takeaways
  • Long-horizon autonomy = trigger (away/scheduled) + self-drive (read SOP) + trace (memory/L4).
  • autonomous.py is the minimal example; scheduler.py drives scheduled tasks.
  • Rules in autonomous_operation_sop / scheduled_task_sop / supervisor_sop.
💡 Design Insight
The seemingly advanced "long-horizon autonomy" introduces no new core — it just snaps together three old blocks: reflection probes + layered memory + SOPs: probes decide "when to act", SOPs decide "what to do", memory ensures "do not forget, do not repeat". Almost all of GA's complex abilities arise this way, composed from simple parts rather than by piling on new mechanisms — the secret to how "3K lines of seed code" grows into a towering tree.
