Agent Loop 核心拆解The Agent Loop

整个 GenericAgent 的“心跳”就是一个约 100 行的循环——agent_loop.py: agent_runner_loop。它不断地：把消息交给大模型 → 看模型想调哪个工具 → 执行 → 把结果带进下一轮 → 再来一遍，直到任务完成或退出。读懂这一个函数，就读懂了 GA 的运行方式。

🌍 宏观理解

很多 Agent 框架把“循环”做得很复杂。GenericAgent 反过来：循环极简，复杂性都推给了大模型和工具。它的循环是逐轮（turn）推进的——每一轮就是“一次模型调用 + 若干次工具执行”，最多跑 max_turns 轮（默认 40）。

一轮里发生了什么

1

调用模型

把当前 messages 与工具 schema 交给 client.chat(messages, tools)，流式拿到回复。

2

解析工具调用

从 response.tool_calls 读出模型想调用的工具与参数；一轮可含多个工具。

3

逐个执行

对每个工具调用 handler.dispatch(...)，得到一个 StepOutcome。

4

决定下一步

收集各工具的 next_prompt 与结果；若有工具要求退出或没有 next_prompt，则结束。

5

组织下一轮消息

只把“这一轮的新消息 + 工具结果”作为下一轮输入，历史由 Session 保存。

agent_loop.pyagent_runner_loop
while turn < handler.max_turns:
    turn += 1
    # 每 10 轮重置一次工具描述，省 token
    if turn % 10 == 0: client.last_tools = ''
    response = yield from client.chat(messages, tools_schema)
    tool_calls = [...]  # 来自 response.tool_calls
    for tc in tool_calls:
        outcome = yield from handler.dispatch(tc.name, tc.args, response)
        if outcome.should_exit: ...
        if not outcome.next_prompt: ...  # 任务完成
    # 只带新消息进下一轮，历史在 Session 里
    messages = [{"role": "user", "content": next_prompt, "tool_results": tool_results}]
🔬 源码对应
  • 入口函数 agent_runner_loop(client, system_prompt, user_input, handler, tools_schema, max_turns=40, ...)，初始 messages 为 [system, user] 两条。
  • 每个工具返回一个 StepOutcome(data, next_prompt, should_exit)（dataclass）：data 是给模型看的结果，next_prompt 是下一轮提示，should_exit 表示主动退出。
  • 三种结束：某工具 should_exit → EXITED；没有 next_prompt → CURRENT_TASK_DONE；轮数耗尽 → MAX_TURNS_EXCEEDED。

⚙️ 内部怎么走

一轮 = 一次 client.chat（拿到 response）→ 解析 tool_calls → 逐个 dispatch 执行（收集 tool_results / next_prompts / exit_reason）→ turn_end_callback 拼出 next_prompt → 把新消息塞进 messages，回到 while 顶部。整个函数只有约 65 行，没有任何隐藏状态机。

❓ 为什么用 yield from

response = yield from client.chat(...) 既能把模型的流式输出实时透传给上层（边想边显示），又能在生成器结束时用 return 拿到最终的 response 对象。一行兼顾“流”和“结果”。

❓ 为什么要造 no_tool

当模型这一轮没有调用任何工具（往往意味着它想直接回答或已经做完），循环不会特判，而是塞一个虚拟的 no_tool 进 tool_calls，统一交给 dispatch。dispatch 里对应 do_no_tool，由它判断是“任务完成”还是“空回复需重试”。这样主循环对“有没有工具”始终走同一条代码路径。

3 三种结束：EXITED / CURRENT_TASK_DONE / MAX_TURNS_EXCEEDED 点击展开
🧪 判定代码
agent_loop.pyagent_runner_loop
if outcome.should_exit:
    exit_reason = {'result': 'EXITED', 'data': outcome.data}; break
if not outcome.next_prompt:
    exit_reason = {'result': 'CURRENT_TASK_DONE', 'data': outcome.data}; break

🔀 三者区别
结果触发条件含义
EXITED某工具 should_exit=True主动退出（如 ask_user 多次空回）
CURRENT_TASK_DONEoutcome.next_prompt 为空本轮没有下一步提示 = 任务自然结束
MAX_TURNS_EXCEEDEDwhile 跑满 max_turns兜底上限，默认 40 轮
⚠️ 坑点：next_prompt 为空就等于完成

工具作者要注意：只要返回的 StepOutcome.next_prompt 是 None/空串，循环就判定 CURRENT_TASK_DONE 并 break。想让任务继续，必须给一个非空的 next_prompt（哪怕只是 '\n'）。这就是为什么 do_code_run 等工具都用 _get_anchor_prompt() 返回一段非空提示。

⚙️ 三件事各做什么
  • max_turns=40：默认最多 40 轮，是防止无限循环的硬上限（计划模式会被抬到 100/120）。
  • turn%10==0 → client.last_tools=''：每 10 轮把“工具库已激活”的缓存清空，强制下一次把完整工具描述再发一遍，防止长跑后模型“忘了”工具协议。
  • messages=[新消息]：下一轮 messages 只有这一条新内容，历史完全交给 Session——循环本身几乎无状态。
🔀 对比：把历史塞进 messages 的传统写法

很多框架每轮把全部历史追加进 messages 再发给模型，messages 越滚越长、循环也越来越难懂。GA 反过来：循环只递新消息，*Session.ask 内部维护 history 并在发送前 trim/compress。职责一分为二——循环管“这一轮”，Session 管“省 token 的历史”。

🧩 生活类比
像一个照着固定节奏干活的工人：看一眼现场 → 想该做什么 → 动手做 → 记一笔 → 再看一眼。工人本身的“流程”很死板、很短，但因为每一步“想该做什么”交给了聪明的大脑（大模型），所以这套简单循环能完成非常复杂的任务。

💡 设计亮点
最妙的一行是 messages = [ 新消息 ]：循环不把历史塞进 messages，每轮只递“这一轮新增的内容”，历史交给 Session 单独管理。这让循环本身几乎无状态、极易理解，也为后面“把上下文压到 <30K”的 token 效率埋下伏笔——少即是多，从这一行开始。

The "heartbeat" of all of GenericAgent is one ~100-line loop — agent_loop.py: agent_runner_loop. It repeatedly: hands messages to the LLM → sees which tool the model wants → runs it → carries the result into the next round → and goes again, until the task is done or it exits. Understand this single function and you understand how GA runs.

🌍 The Big Picture

Many agent frameworks make the "loop" elaborate. GenericAgent does the opposite: the loop is tiny and pushes complexity onto the model and the tools. It advances turn by turn — one turn is "one model call + zero or more tool runs" — for at most max_turns turns (default 40).

What happens in one turn

1

Call the model

Hand the current messages and tools schema to client.chat(messages, tools) and stream back the reply.

2

Parse tool calls

Read response.tool_calls for the tools and arguments the model wants; a turn may contain several.

3

Run them one by one

For each call, invoke handler.dispatch(...), yielding a StepOutcome.

4

Decide what is next

Collect each tool's next_prompt and results; if a tool asks to exit, or there is no next_prompt, finish.

5

Build next-turn messages

Pass only "this turn's new message + tool results" as the next input; history is kept by the Session.

agent_loop.pyagent_runner_loop
while turn < handler.max_turns:
    turn += 1
    # reset tool descriptions every 10 turns to save tokens
    if turn % 10 == 0: client.last_tools = ''
    response = yield from client.chat(messages, tools_schema)
    tool_calls = [...]  # from response.tool_calls
    for tc in tool_calls:
        outcome = yield from handler.dispatch(tc.name, tc.args, response)
        if outcome.should_exit: ...
        if not outcome.next_prompt: ...  # task done
    # only the new message goes to the next turn; history lives in the Session
    messages = [{"role": "user", "content": next_prompt, "tool_results": tool_results}]
🔬 In the Source
  • The entry function agent_runner_loop(client, system_prompt, user_input, handler, tools_schema, max_turns=40, ...) starts messages as two entries [system, user].
  • Each tool returns a StepOutcome(data, next_prompt, should_exit) (a dataclass): data is the result shown to the model, next_prompt is the next-turn prompt, should_exit means exit on purpose.
  • Three endings: a tool sets should_exit → EXITED; no next_prompt → CURRENT_TASK_DONE; turns exhausted → MAX_TURNS_EXCEEDED.

How it flows

One turn = one client.chat (get the response) → parse tool_calls → dispatch each (collecting tool_results / next_prompts / exit_reason) → turn_end_callback builds next_prompt → stuff the new message into messages and jump back to the top of the while. The whole function is only ~65 lines, with no hidden state machine.

Why yield from

response = yield from client.chat(...) both passes the model's streaming output through to the caller in real time (show as it thinks) and, when the generator finishes, grabs the final response object via return. One line covers both "stream" and "result".

Why fabricate no_tool

When the model calls no tool this turn (often meaning it wants to answer directly or is done), the loop does not special-case it — it injects a virtual no_tool into tool_calls and hands it to dispatch like any other. Dispatch maps it to do_no_tool, which decides whether this is "task done" or "blank reply, retry". So the main loop always takes the same code path whether or not a tool was called.

How the three differ
ResultTriggerMeaning
EXITEDa tool sets should_exit=Truedeliberate exit (e.g. repeated blank replies)
CURRENT_TASK_DONEoutcome.next_prompt is emptyno next-turn prompt = task naturally finished
MAX_TURNS_EXCEEDEDwhile exhausts max_turnsthe safety cap, default 40 turns
Pitfall: empty next_prompt means done

Tool authors beware: if the returned StepOutcome.next_prompt is None/empty, the loop decides CURRENT_TASK_DONE and breaks. To keep going you must return a non-empty next_prompt (even just '\n'). That is why tools like do_code_run return a non-empty prompt via _get_anchor_prompt().

The three key lines

                      tools_schema, max_turns=40, ...):
    ...

What each line does
  • max_turns=40: at most 40 turns by default — the hard cap against infinite loops (plan mode raises it to 100/120).
  • turn%10==0 → client.last_tools='': every 10 turns it clears the "tools already active" cache, forcing the full tool description to be re-sent so the model does not "forget" the tool protocol over a long run.
  • messages=[new message]: the next turn's messages holds only this one new entry; history is entirely delegated to the Session — the loop itself is almost stateless.
vs the classic "stuff history into messages"

Many frameworks append the entire history into messages each turn before sending, so messages keeps growing and the loop gets harder to follow. GA inverts this: the loop passes only the new message, while *Session.ask maintains history internally and trims/compresses it before sending. Responsibilities split cleanly — the loop owns "this turn", the Session owns "token-thrifty history".

🧩 Analogy
Like a worker following a fixed rhythm: glance at the scene → think what to do → do it → jot a note → glance again. The worker's own "procedure" is rigid and short, but because the "think what to do" step is delegated to a smart brain (the LLM), this simple loop can finish very complex tasks.
✅ Key Takeaways
  • The core is one function, agent_runner_loop (~100 lines), advancing turn by turn, up to 40 turns by default.
  • Each turn = one model call + some tool runs; tools return a StepOutcome.
  • The next turn carries only the new message; the Session maintains history.
💡 Design Insight
The cleverest line is messages = [ new message ]: the loop does not stuff history into messages; each turn passes only "what is new this turn", leaving history to the Session. This keeps the loop almost stateless and easy to grasp, and it sets up the later "keep context under 30K" token efficiency — less is more, starting from this one line.
